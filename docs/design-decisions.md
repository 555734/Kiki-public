# 設計上の判断

企画書『SIDE / SKY（仮）』および添付モックアップ 3 枚から、意図的に変えた点と
その理由。実装中に見つかった資料同士の矛盾も、ここで決着させている。

---

## 1. 企画書とモックアップが食い違っていた点

### P2 のヘッダーはハートではなくゲージ

モックアップ 2 と 3 は P2 ORION にもハート 4 つを描いているが、モックアップ 1 は
ゲージバーになっている。企画書 3 章は明確に

> ガーディアン単独の「死亡」はない。

と書いているので、**モックアップ 1 が正**と判断してゲージバーを採用した。
ガーディアンが常時見るべき数字はゲージ以外にないので、実用上もこちらが正しい。

### 弾数「3/3」はゲージから導出する

モックアップ 3 のスコープには `3/3` のマガジン表示がある。一方、企画書 4 章の
狙撃はゲージ 20 消費で、弾数という第 2 のリソースは存在しない。

二重リソースにすると管理が増えて企画書 9 章の「操作過多」に触れるので、
**表示だけをゲージから導出**した。

```gdscript
static func ammo_for(gauge: float) -> int:
    return mini(int(floor(gauge / Balance.COST_SNIPE)), Balance.SNIPE_AMMO_DISPLAY_CAP)
```

満タンなら 3/3、40 なら 2/3。絵は再現され、数値設計は 1 本のまま。

### 倍率スライダーは 3 段に

モックアップは 1x〜6x の連続スライダー、企画書 6 章は「倍率は固定から開始し、
複雑化を避ける」。折衷して **2x / 3x / 4x の離散 3 段**（既定 3x）。
スライダー UI は残しつつ、刻みだけ 3 つにしてある。

### 能力アイコンの `∞` はコスト表示に

モックアップは各能力の下に `∞` を置いているが、この設計で無限なのは
「使用回数」であってゲージではない。ゲージこそが企画書 4 章の中核制約なので、
**コスト（30 / 25 / 20）を表示**し、払えないときは減光する。

## 2. スコープを全画面にしなかった理由

モックアップ 3 は画面全体を占める FPS スコープを描いている。これは各自が
自分の端末を持つ前提の絵で、**1 台のタブレットを共有する本実装では成立しない**。
ガーディアンが覗いた瞬間、ランナーはジャンプの最中に画面を奪われる。
これは企画書 9 章がリスク表の筆頭に挙げている

> 見えない敵に殺される／ランナー側が理不尽

そのものになる。

なので拡大は**レティクル周辺のリング内だけ**にした。

- リングの中身は `World2D` を共有した `SubViewport`（シーンの複製ではない）
- 外側は減光のみ。しかも `Balance.SCOPE_DIM_MAX_ALPHA = 0.35` が硬い上限
- 目盛り・十字線・赤い中心点・倍率表示・弾数はモックアップ通りリング内に再現

副次的な利点として、非スコープ時は `render_target_update_mode = UPDATE_DISABLED`
にできるので、常時 2 画面描画のコストを払わずに済む。モバイルではこれが効く。

## 2.5 アートを「モックアップからの切り出し」にした理由

第1段階では画像素材ゼロ・全部コード描画で作った。その天井にぶつかったので、
実画像素材に切り替えている。ただし**私に画像を生成する手段はない**。使える塗りの
素材はいただいたモックアップ3枚だけで、逆に言えばそれがアートディレクション
そのものなので、そこから切り出すのが最も一致する。

`tools/extract_assets.py` が3枚から34点を抜く。手法は、クロップの縁に現れる色を
すべて背景の参照色とみなし、そこからの距離が近い画素のうち**縁に接続している成分
だけ**を背景として落とす方式。単純な色距離だと隅に茶色が写り込んだだけで茶色い敵が
消えるが、連結成分を見るのでそれが起きない。空に対する白い雲のように色が近すぎる
被写体には、チャンネル式のキー（`r-b` が空より小さい＝雲、など）を使い分けている。

写っていない **飛行敵・砲台・弾・レーザー・スイッチ・扉・移動床・チェックポイント・
ゴール** は `tools/synthesize_assets.py` が切り出した部品から組む。歩行敵の体に羽を
足して飛行敵、パイプの金属質感とレンガの陰影を鋼色に転色して砲台、ホログラムの発光を
橙に転色して弾、という具合。同じ塗り・同じ光源から作っているので画面上で浮かない。

地形は300〜460pxの帯を1枚ずつ切り出し、**半分ずらして継ぎ目をクロスフェード**して
タイル化している。さらに、元が絵画からの切り抜きである以上そこには元の照明勾配が
焼き込まれているので、強くぼかした複製で割って平均を戻し、勾配だけ捨てている
（これをやらないと、9,000px のステージに縞が出る）。

**この方式の限界。** ランナーのポーズは3枚しか存在しないので、手描きの走りサイクルは
作れない。ポーズ切替＋着地スクワッシュ・空中ストレッチ・傾き・上下動で補っている。
合成した敵は塗りと光源こそ揃うが「描き下ろし」ではない。後から画像をいただければ
`src/render/art.gd` の登録簿を差し替えるだけで入る。

## 3. シーンではなくコードで組んでいる理由

`.tscn` は `main` とテスト用の 3 つだけで、エンティティもレベルもコードから構築している。
一般的な Godot の作法ではないので、理由を書いておく。

- **絵に配置するものがない。** スプライトは登録簿（`src/render/art.gd`）経由で
  描画時に引かれ、地形はレベルデータの矩形からタイル描画される。エディタで見ても
  空のノードが並ぶだけで、視覚的に編集できる情報が存在しない。
- **レベルはデータの方が速い。** 企画書 8 章の P2 段階は「ゲージ・持続時間・
  敵密度を何度も調整する」フェーズで、`level_01_data.gd` の数値を書き換える方が
  巨大な `.tscn` のノードを掴んで動かすより速く、差分も読める。
- **検証できる。** 座標がデータなので、到達性監査とペース監査をテストとして
  書ける（後述）。シーンに埋まっていたらこれは書けない。

代償として、エディタ上で地形をドラッグして直すことはできない。
量産フェーズ（企画書 P4）に入るならレベルエディタを別途用意するのが素直。

## 4. 数値の根拠

ランナーの移動値は企画書に記載がなかったので新規に決めた。決めたあと、
その値から**逆算してステージの穴を設計**している。

数値は手で書いた定数ではなく、**`_test_runner_arc()` が実際の物理ボディを飛ばして
毎回測っている**。`tools/verify.sh` がその実測値を印字する。

| | |
|---|---|
| 歩きジャンプ | 到達距離 **193px** / 最高点 **133px** |
| スプリントジャンプ | 到達距離 **226px** |
| スプリント＋空中ダッシュ | 到達距離 **326px** |
| 足場 1 枚を挟む | **602px**（226 + 足場幅 150 + 226） |

したがって:

- 150px の穴 → ジャンプだけで越える（チュートリアル）
- 300px の穴 → スプリントと空中ダッシュが要る
- **600px の穴 → 足場なしでは絶対に越えられない**（区間 A の山場）

**この数字は到達性監査が直接食う。** 以前は監査側に `plain_jump = 206.0` /
`sprint_jump = 330.0` とベタ書きしてあって、実測（193 / 226）と最大 100px ずれていた。
実測値を流し込むように変えた瞬間、**区間 F の最後の 620px の穴が
「足場を 1 枚置いても届かない」で落ちた**——つまりステージが最後の直前で
詰んでいた。穴を 540px に詰めて解消してある。

空中ダッシュは `velocity.y = 0` を入れるので、**上昇中に撃つとジャンプを捨てることになる**
（測ると 326px → 181px まで落ちる）。頂点で撃つのが正しい使い方で、
監査もその前提の値を使う。

## 5. テストで固定した「設計の約束」

普通のユニットテストに加えて、企画書の成功条件をそのままテストにしたものが 3 つある。

### ガーディアン退屈監査

企画書 8 章は MVP の成功判定に

> 神側が暇にならない。10 秒以上、何もすることがない区間がほぼない。

を挙げている。これを、敵・ギミック・足場を要求する穴の x 座標を全部並べて、
**隣り合うタスクの最大間隔を走行速度で割る**という形で数値化した。
現状の最長無タスク区間は **4.4 秒**（ステージを 6 区間に組み直す前は 7.6 秒）。
10 秒を超えたらテストが落ちる。

### ステージ到達性監査

静的地形に加えて移動床と崩落床の占有範囲も足したうえで、すべての穴が
上記 202 / 365 / 554 のいずれかで越えられるかを検算する。
実際にこの監査が、区間 B の 600px の穴を「移動床を数えていない」状態で
一度検出している。

### タッチ配置監査

二人が同じ画面を触るので、ランナーのボタンとガーディアンのボタンが
1 つも重ならないこと、スティック領域が仕切りを越えないことを検査する。

## 6. 実装中に見つかった不具合

**踏みつけが原理的に成立していなかった。**

ランナーの `collision_mask` は意図的に敵を含んでいない（敵に押されて動かされる
のを防ぐため）。ところが当初、踏みつけ判定を `get_slide_collision()` で
書いていたので、**物理衝突が存在しない相手を踏んだか判定しようとしていた**。
歩行敵は永久に踏めなかった。

`_test_stomp_and_damage` がこれを検出し、判定をハートボックスの毎フレーム
走査に移して修正した。ついでに「すでに重なっている状態」（リスポーン直後や、
立っているランナーに敵が歩いてきた場合）も拾えるようになっている。
`area_entered` は進入の瞬間しか撃たないので、こちらの方が正しい。

**その後、踏みつけ自体をやめた。** recovery で「敵への接触はすべて被弾」に
変更した（`419d37e`）。上から乗っても敵は死なず、ランナーがダメージを受ける。
敵を倒すのはガーディアンの狙撃だけになり、ランナーが単独で解決できる脅威を
減らしている。上のハートボックス走査はそのまま被弾判定として生きている。
`_test_stomp_and_damage` も現在はこの契約を検査している。

## 6.5 実機で触ってわかったこと

### 仮想スティックが相対ドラッグ式だった

**症状**：「押して、少し進んで、止まる」。

原因は、スティックが**指を置いた場所を原点にして、そこからのドラッグ量**で軸を
決めていたこと。多くの仮想スティックはこの方式だが、この操作系では致命的だった：
押して保持しても偏位はゼロなので、指を滑らせている間しか動かず、止めた瞬間に
それ以上の入力が来なくなる。しかも `_touch_down` が `move_axis = 0` を代入していた
ので、押した瞬間は必ず停止していた。

**位置指定式**に変更した。原点はゾーン中央に固定し、軸は**指が今どこにあるか**で決まる。
中央より左を押せば即座に左、押しっぱなしで走り続ける。原点は画面に描いてあるので
狙える。ベゼルを握った手のひらが常時左入力にならないよう、ゾーンは画面端から少し
内側に寄せてある。

回帰テスト `_test_virtual_stick()` は、**ドラッグを一切せずに押しただけ**で軸が立ち、
保持中に減衰せず、実際にランナーが動くことを検証する。

副次的に見つかった不具合：`_has_touch` が `_unhandled_input` でしか立たなかったため、
タッチ経路を通ってもデスクトップ用のポーリングが `move_axis` を毎フレーム 0 で
上書きし得た。どのタッチ経路でも立つようにした。

### ボタンがスティックの判定を食っていた

DASH ボタンの当たり円がスティックのゾーンに重なっていた。`_touch_down` はゾーンより
先にボタンを判定するので、**スティックの右側が丸ごと死んでいた**。ランナーの操作系は
仕切りより左に全部収める必要があって窮屈なので、目視ではなくテストで担保するようにした
（`test_touch_layout_separation()`）。

### 土管とブロックをすり抜けていた

これは実装通りの挙動で、私が装飾として作っていた。ただしマリオ的な文脈では土管と
ブロックは固体であるべきで、期待の方が正しい。実体を持たせた。

サイズを `level_01_data.gd` の `size` に明示し、**描画も当たり判定も同じ矩形から作る**
ようにしたので、絵と物理がずれることはない。柵・木・花は装飾のまま——足首の高さに
あって、見てもぶつかる理由が分からない障害物になるだけだから。

土管はすべてジャンプ到達高（100px）より低く、浮遊ブロックの下はランナーの背丈より
広い。`test_solid_decor()` がそれを検算し、湧き位置やチェックポイントの上に固体が
乗っていないことも見る。

### タップジャンプが背丈より低かった

**症状**：「ジャンプしながら進むとかができなさすぎる」。

可変ジャンプの**カットを毎フレーム掛けていた**のが原因。ボタンを離した瞬間に
一度だけ上昇を削るつもりのコードが、離している間ずっと `velocity.y *= 0.55` を
掛け続けていたので、複利で潰れていた。

修正前のコードに戻して実測した数値がこれ（`tools/verify.sh` が毎回この行を印字する）：

| | 修正前 | 修正後 |
|---|---|---|
| 50ms のタップ（親指が実際にやる長さ） | **39px** | **96px** |
| 押しっぱなし | 133px | 133px |

ランナーの身長は 46px。**タップでは自分の背より低くしか飛べていなかった**。
これでは走りながらの小ジャンプが成立しない。押しっぱなしだけは正常だったので、
デスクトップのキーボードで触っている限り気づけない類の不具合だった。

修正は 2 つ。①**押し始め 0.15 秒はカットしない**（`RUNNER_MIN_JUMP_TIME`）、
②カットは離した瞬間の**1 回だけ**（`_jump_cut_used`）。あわせて落下側の重力を
上昇側より重くした（1500 → 2100）。上りが速く下りが締まるのは 2D アクションの
定石で、滞空が短くなるぶん「跳んだ先が読める」。

`_test_runner_arc()` が、タップで身長の 1.5 倍を超えることと、
タップが押しっぱなしより低いままであることの両方を固定している。
横の到達距離 193px も同じテストが見ていて、ステージの穴の幅はこの数字を基準に
決めてある。

### 走りながらジャンプする手が足りなかった

ボタンが JUMP と SPRINT の 2 つになっても、**片手しか空いていない**場面
（もう片方でタブレットを支えている、相手と肩を並べている）では、スティックから
親指を離さずにジャンプする手段が無かった。

スティックのリング上部を**ジャンプゾーン**にした。指を travel の 52% より上へ
押し上げるとジャンプが入り、そのゾーンに居る間は「JUMP 押しっぱなし」と同じ
扱いになる（＝深く倒すほど高く飛ぶ）。横の軸は指の x 座標のままなので、
**走りが途切れない**。押し上げっぱなしで連続ジャンプにならないよう、
発火はゾーンへ入る瞬間の一度だけ（`_jump_latched`）。

FPS のパッドを参考にした結果、ボタンは 2 つとも**スティックの右側に縦積み**に
なっている。ランナーの操作系は仕切りより左（画面の 30%）に収める必要があり、
その中で親指 2 本が届く並びはこれしかない。配置はハードコードではなく
`TouchLayout.runner_cluster()` が画面サイズから計算し、
`test_touch_layout_separation()` が 5 種類のアスペクト比で
「ボタンがスティックの判定を食わない」「画面からはみ出さない」を検算する。

### 崩落床だけ素材が当たっていなかった

スクリーンショットを撮って気づいた。周りの地形が全部塗り込まれている中で、
崩落床だけが**単色の茶色い矩形**で、そこだけ試作品に見えていた。テクスチャ化の
パスから漏れていた。地面と同じ草＋土のタイルに差し替えたうえで、
「これは崩れる床だ」と分かるよう**常時見えるひび**と、作動後の**橙の色被り**を
足した。地形と同じ材質にしたのは、まず「床だ」と読めないと踏んでもらえないから。

### ステージ看板が敵を隠していた

右上のステージ看板の裏に、砲台や飛行敵がちょうど入る。ガーディアンが撃つべき
相手が HUD で見えないのは筋が通らないので、看板は開始 5 秒で 42% まで落ちる。
目標マーカーのダイヤだけは全強度のまま残す（小さいので何も隠さない）。

### 到達性監査が「実測」ではなく「ベタ書き」だった

これは今回いちばん危なかった。到達性監査は「すべての穴は越えられる」を保証する
テストなのに、その根拠になるジャンプ到達距離を**テストの中に数字で書いて**いた。
`_test_runner_arc()` は別に実物を飛ばして測っていたのに、その値は監査に流れていなかった。

実測値を流し込むように変えたら、ベタ書き（206 / 330px）と実測（193 / 226px）が
最大 100px ずれていて、**区間 F の最後の 620px の穴が
「足場を 1 枚置いても届かない」で即座に落ちた**。ゴール直前で詰むステージを、
「全チェック通過」と表示したまま出しかけていた。

- 穴を 540px に詰めた
- 監査の 4 つの到達距離は `_test_runner_arc()` の実測値を受け取る
  （ベタ書きは単体実行時のフォールバックとしてだけ残した）
- 実測値は `tools/verify.sh` が毎回印字する

「テストがあるから安心」ではなく、**そのテストが何を根拠にしているか**まで見ないと
意味がない、という具体例。

### 敵が勝手に居なくなっていないか

スクリーンショットを撮ったとき、区間 A の歩行敵——踏みつけを教えるための 1 体——が
画面に居なかった。原因は撮影スクリプト側だったが、
「巡回が自分の足場から落ちて死ぬ」なら本物の不具合で、しかも
**他の全チェックを通したまま静かに成立してしまう**。

`_test_enemies_hold_their_ground()` を足した。ランナーを遠くに置いたまま 12 秒回し、
歩行敵の数が減らないことと、誰も奈落の高さに落ちていないことを見る。

### スコープは壊れていなかった（撮影が的外れだった）

「スコープが描画されていない」ように見えるスクリーンショットが続いていた。実際には
撮影スクリプトが**画面外 1900px の敵**を狙っていただけで、スコープ本体は正常。
紛らわしかったのは、スコープの付属表示（倍率バッジ・弾ストリップ）が
`_clamp_to_screen()` で画面内に引き戻される作りだったこと——リングだけ画面外に消え、
バッジは端に残るので、「リングが描かれていない」と読めてしまう。

撮影は固定の画面内座標を狙うようにした。ついでに、リング下端の弾ストリップが
画面下の能力バーと重なっていたのを、下が詰まっているときはリングの上に出すよう直した。

## 6.55 ガーディアンが「置きたい所に置けない」理由（実機からの3件目）

> 「状態管理をやめて。狙撃ボタン、足場ボタンをそれぞれ作って。
> 　狙撃も足場も確定ができなくなっている。空中に浮いていることが多すぎる」

同じ指摘が3回目なので、今度は**推測をやめて実機と同じ経路で再現した**。
`test/ui_probe.gd` に、実際の指の動きを流し込むチェックを足したところ、
2件の不具合が**その場で再現した**。

### 1. 能力バーが、狙うための指を食っていた

能力バーは画面下端（y=0.838）にある。そして**地面も画面の下にある**。
「地面をタップして狙う → 道具ボタンを押す」という流れは、
狙うための指が**バーそのものに当たる**ことを意味していた。
当たると道具が発動し、**古い照準の位置に**構造物が出る。

プローブでの再現：画面下部をタップ → 照準は 1px も動かず、
代わりに選択中の道具が 3 → 1 に変わった。
利用者の言う「置きたい所に置けない」「確定できない」はこれ。

**直し方：道具ボタンから引き出す。** ボタンを押している間がその道具で、
指を離した所が確定。狙うためにバーのある場所を触る必要がなくなる。
モードも消える——「選択された道具」という状態が存在しない。

指の下は見えないので、ゴーストは指より画面高さの 9% 上に出す
（`TouchLayout.DRAG_LIFT`）。26px の足場は指で完全に隠れるし、
「ランナーの足元か頭の上か」はこのゲームの全部なので。

### 2. 照準が「画面の座標」だった

`aim_screen` は**スクリーン座標**で保持され、読むたびにワールドへ変換していた。
カメラはランナーを追う。つまり**照準はランナーが走るぶんだけ地面の上を滑る**。
狙ってからボタンに手を伸ばす 0.5 秒で、目標は別の場所になっている。

プローブでの実測：カメラを 260px 動かすと照準は **121px** ずれた。
最初に書いたチェック「狙った所に建つ」は **32px 外して落ちた**。

**直し方：`aim_point` をワールド座標で持つ。** 画面座標は描画用の記録に降格。

この不具合は**既存のテストを1つ通していた**。`_test_one_press_tools` は足場と壁を
同じ点に置いて両方成功していたが、それは 2 回のタップの間に照準が
勝手にずれて壁が足場を避けていたからだった。
**捕まえるべきバグのおかげで通っていたテスト**で、今は両方の着地点を明示的に検査する。

### 3. 「空中に浮いている」を絵から測った

配置データと定数を突き合わせる検査は、ゲームがやるのと同じ計算をするので、
**定数が間違っていれば検査もろとも間違う**。そこで `test/seating_probe.gd` は
**描画されたピクセル**を測る：被写体を消した前後のフレームを差分して
スプライトの最下端を求め、地形を消した前後の差分で草の最上端を求め、その差を返す。

途中で出た誤測定も、そのまま設計上の教訓になっている。

| 症状 | 原因 |
|---|---|
| 全部が 450px 沈んで見えた | 雲と草が動いていた。差分がフレーム全体で出る。→ `Engine.time_scale = 0` と `paused` で世界を止め、「隠して戻したら絵も戻るか」という**自己検査**を入れた |
| 全部が「何も描かれていない」 | カメラはランナーしか追わないので、被写体の所に**ランナーごと**移さないと画が動かない |
| 装飾 33 個が黙って消えた | `decor.items` は `Array[Dictionary]` で、素の `Array` を代入すると実行時エラー。コルーチンが落ちて行が出ない |
| チェックポイント5本が +67px 浮いていた | 被写体中心の細い帯で測っていたが、旗の**支柱は帯の左外**にあった。帯をやめて**画面全体の差分**にしたら -3px（正しい） |

そうして残った、本物の不具合が**砲台5基が 19px 浮いていた**こと。
既存の接地検査は「砲台は据え付けだから」と**除外していた**。
実際に据え付けなのは渡り廊下の上に吊られた 1 基だけで、
残り 5 基は地面に座るべきものが 19px 浮いていた。

副作用として、**砲台の弾はランナーの頭の上を通っていた**。
ランナーの中心は地面から 23px 上、砲台の弾は 45px 上に出ていたので、
「壁で防ぐべき脅威」は当たらない脅威だった。直すと当たるようになる——
つまりセクション B と C は**設計どおりの難度に戻る**。

検査も直した。接地検査は砲台も見るようになり、
「空中に居てよい敵はちょうど 1 体」という条件を付けた
（砲台を元の位置に戻すと落ちることを確認済み）。
浮いている `?` ブロックは**意図的に空中**なので対象外にしてある。

## 6.8 「0.5秒遅れる」「10秒で切れる」の正体

> 「繋がりはしたが、タイムラグが0.5秒くらいあり、なおかつ10秒くらいプレイしたら
> 　接続切れて繋ぎなおしていますという表示がずっとされている。根本的に改善不可能？」

**改善可能だった。** どちらも中継のせいではなく、こちらのコードの問題。

### まず中継を無罪にする

実際のゲームと同じ通信量（ホスト→30/秒、ゲスト→60/秒）を本物の中継に45秒流した：
**RTT 33ms 一定・エラー0・損失0.1%・切断なし**。0.5秒はここにはない。

次に、**Godot 2プロセスを本物の中継につないで実セッションを走らせる**
（`test/net_live_probe.gd`）。これが決め手になった。ゲスト側の毎秒レポートに
`buf=20`（スナップショットのバッファが常に満杯）と `interp=3`（最小値に張り付き）が
出ていて、**受信は足りているのに表示が追いついていない**ことが見えた。

### 原因1：クライアントの時計が止まっていた（＝0.5秒）

`Clock._physics_process` は `if is_host: tick += 1`。
つまり**ガーディアンの端末では tick が自力で進まない**。
進むのは `Clock.tick` を代入している場所だけで、それは
WELCOME（最初の1回）と **PONG（毎秒1回）**しかなかった。

描画位置は `Clock.tick - _interp_ticks` で決まる。
だから**世界は1秒止まって、60tick 分ワープする**。平均すれば0.5秒古い。
利用者が言った「0.5秒くらい」はそのままの数字だった。

スナップショットは毎秒30回、正しい時刻を運んできていた。
しかし**それを読んでいなかった**。

**直し方：時計は時計なので、走らせる。**
クライアントでも毎フレーム tick を進め、受信した host の tick に向かって
1フレーム1tickずつ**寄せる**（大きくずれたときだけ跳ぶ）。
スナップショット30回/秒が舵になる。

副産物として、16bit で送っている tick の**18分ラップ**も直した
（`Clock.widen`）。それまでは18分を超えると host の時計が18分巻き戻っていた。

### 原因2：照準を毎フレーム送っていた

`_send_aim()` は `_process` から無条件に呼ばれていた。
60fps の端末で 60通/秒、120fps の端末では 120通/秒。
**スナップショット(30/秒)の2〜4倍**を、親指の位置のために送っていたことになる。

中継は**順番どおりに転送する**ので、ガーディアン自身の洪水が、
ガーディアンが待っているスナップショットの前に並ぶ。
負のコントロールで実測すると **145通/秒**出ていた。

20Hz に制限。実測でゲストの送信は **62通/秒 → 16通/秒**（約4分の1）。

### 原因3：健全なソケットを捨てていた（＝「ずっと繋ぎ直しています」）

再接続の監視は「4秒無音なら再ダイヤル」だった。しかし
**ソケットが OPEN のままの無音は、こちらの接続が切れたのではなく相手が黙っただけ**。
そこでソケットを作り直すと、中継の部屋は2人分しかないので
**古いソケットが枠を握ったまま新しいのが `room is full` で弾かれる**。
一度発動したら二度と戻れない——「ずっと表示されている」の正体。

しかも `close()` した Peer を捨てると、**誰も poll しないので close が完了しない**。
枠は解放されないままになる。

直し方：**OPEN なソケットは絶対に捨てない**（HELLO を送り直すだけ）。
本当に閉じるときは、閉じ終わるまで `_closing` に入れて poll し続ける。

### 実測（同じ中継・同じコード・36秒）

| | 前 | 後 |
|---|---|---|
| 表示の遅れ | 1秒ごとに0→1秒（平均0.5秒） | **16〜33ms** |
| ゲスト送信 | 62通/秒（端末次第で145通/秒） | **16通/秒** |
| 切断 | — | なし |

### 諦めずに済むように

90秒の再接続に失敗したら、**接続画面に戻る**ようにした。
凍った世界の上に帯が出たまま押せるものが何もない、という状態をやめる。
接続診断には**いま動いているセッションの数字**（受信数・往復・時計と最新
スナップショットの差・無音の長さ）も出るようにした。

## 6.9 ボタンを丸くして、動かせるようにした

> 「ガーディアンの画面もキャラクターの画面も、この参考画像のように、
> 　指が届く位置に、丸ボタンで配置して。あと、ボタンの位置は自由に動かして設定できるように」

参考にいただいたのはモバイルFPSの画面。要点は**丸いこと**ではなく、
**親指が支点から動かずに届く弧に並んでいること**だった。

### まず、置き場所を1箇所にまとめた

これまで配置は3箇所に散っていた：`TouchLayout` の定数、`InputHub` の当たり判定、
`hud_canvas` の描画。**同じ数字の写しが3つある**状態で、
ずれると「見えているのに押せないボタン」になる。プレイヤーに回避手段が無い唯一の不具合。

`ControlLayout` に集約した。入力ルータも HUD も配置エディタも、ここだけを読む。
だから**ドラッグして動かしたものが、そのまま押せる場所になる**。

### 幅基準をやめて、隅からの高さ基準にした

旧実装は x を**画面幅の割合**、半径を**高さの割合**で持っていた。
16:9 では成立するが、4:3 では `x=0.945, r=0.075` が右端をはみ出す。
**他人の端末でしか出ない**種類の不具合。

今は全部、**親指の支点になる隅からの、画面高さ単位のオフセット**。
どんな比率でも隅との関係が変わらない。

例外は「1台で2人」のランナー側だけ。こちらは仕切り線の左に
スティックとボタン2つが**収まらなければならない**ので、高さではなく
**使える幅から**逆算してクラスタ全体を縮める（4:3 では仕切りまで 288px しかない）。

### 監査を1本にして、範囲を広げた

旧テストは2本あって、ランナーのクラスタと「ガーディアンのボタンが仕切りを越えないこと」
しか見ていなかった。**ガーディアンのボタン同士**は誰も見ていなかった——
弧に並べ替えた瞬間に効いてくるのは、まさにそこ。

新しい監査は **5種類の画面 × 3モードの全コントロール**について、
画面内に収まっているか・互いに重なっていないか・隅から親指の届く距離かを見る。
さらに**プレイヤーが動かした配置**でも当たり判定が一致するか、
保存して読み直しても残るかまで確認する。

書いた直後に**16件落ちた**。「1台で2人」のスティックとジャンプが重なり、
ジャンプが画面外にはみ出していた。監査が無ければ実機で気付いていた。

### アイコンは「高さ合わせ」ではなく「収める」

最初の描き直しでは、壁アイコンがボタンより1.5倍広く描かれた。
`draw_sprite` は**高さ**でスケールするので、横長の絵は円からはみ出す。
`Art.draw_sprite_fit` を足して、縦横どちらも収まる倍率にした。

ボタンの**文字も消した**。名前を上、コストを下に書いたら、
右端の弧では両方が画面外に流れ出した——
縁に近いボタンほど周りに余白が無いのだから当然だった。
参考画像のボタンにも文字は無い。名前は配置エディタにある（探しに行く場所だから）。

## 6.10 大きさも可変に、左右に振り分け、そして「先を見る」

### 大きさ：ピンチではなくスライダー

ピンチは**2本指より小さいボタンの上で2本指を使う**操作で、
しかも「できる」ことを画面上で示す方法がない。
触ったボタンが選択され、上のスライダーがそれを指す形にした。
**移動と選択が同じ操作**なので、選ぶための一手が増えない。

保存形式は `Vector2`（位置）から `Vector3`（位置＋倍率）へ。
読み込み側は古い `Vector2` も受け付けて「その位置・標準サイズ」と解釈する。

上下限（0.6〜1.8倍）は飾りではない。小さすぎれば親指が外し、
大きすぎれば隣を飲み込む——後者は配置監査が落とす。

### 左右に振り分け

1人で持つ端末では**親指は2本ある**。全部を右の弧に積むのは、
片方の親指を遊ばせているということ。

- **左**：足場・壁・◀◀（作る手）
- **右**：狙撃・ワープ・スコープ・▶▶（見る手）

「1台で2人」だけは例外で、右側だけに残る。左半分には**もう一人の手がある**から。

この変更で既存テストが1件落ちた。ガーディアン端末で左下をタップしたら
「画面全体が照準になる」と検査していたもの——左下にはもうボタンがある。
**新しい仕様のほうが正しい**ので、検査を「左手にもボタンがあること」＋
「空いている中央は照準になること」の2つに書き直した。

### 「先を見る」の境界

企画書6章は「ガーディアンはランナーより1画面先を読む」としているが、
カメラの先読み（`CAMERA_LOOKAHEAD`）だけでは画面の何分の一かしか稼げない。
残りを手動にした。

**ただし必ず有界にする。** ランナーを画面外に置ける視点は、
「先を見る」ではなく「見捨てる」になる。上限は定数ではなく
**ビューポートから計算**する：`画面半分 ÷ ズーム − 150px`。
16:9 の 1280px 幅なら 277px、4:3 の 960px 幅なら 170px。
どの画面でもランナーは必ず残る。

指を離したら**ゆっくり戻す**。即座に戻すと、見ていたものが消える。
リトライ時は**即座に戻す**——そのときはチェックポイントが全てなので。

置ける範囲（`PLACE_MAX_RANGE`）は**ランナーからの距離のまま**。
視点を動かしても遠くに建てられるようにはならないので、
ゲージという制約は手つかず。

## 6.11 「敵に当たっても撃破できない」——親切心が仕込んだバグ

道具をボタンから引き出すとき、**照準を指より画面高さの9%上**にずらしている。
26pxの足場は指で完全に隠れるし、「ランナーの足元か頭の上か」がこのゲームの全部だから。
足場については正しい。

**そのずらしが狙撃にも効いていた。** 実測で **74ワールドpx**。
歩行敵の身長は **42px**。つまり弾は毎回きれいに頭上を通過していた。

置くものは「置く」。撃つものは「狙う」。
狙いが指より一指分ずれるのは、親切ではなく単に間違い。
`TouchLayout.lift_for(slot)` にして、狙撃だけ 0 にした。

再現テストを先に書いて落ちることを確認している
（「指を敵の上に置いて離すと敵が死ぬ」——72px外して落ちた）。

### そして照準補助を入れた

> 「射撃側はFPSのように、やりやすくして」

旧ルールは照準が敵の体から26px以内。スマホでは**指先ひとつ分**で、
しかも動く的を、**ボタンから離したばかりの同じ親指**で狙う。

企画書4章は「狙撃は面を掃除する武器ではなく、危険を1つ消す道具」と言っている。
つまり面白い判断は **何をいつ撃つか**であって、
親指がキノコの指先ひとつ以内に着地したかどうかは判断ではなく**税**である。

2段階にした。照準の**真下にあるものが最優先**、無ければ110px以内で最寄り。
この順序は敵が2体近接しているときに効く——**指している方**が撃たれる。

同時に**ロックオン表示**（赤い四隅マーク）を出した。引き金の前に
「こいつ」と言うのがロックの全部で、これが無ければ撃つことは推測のままになる。
曳光弾も**実際に当たった体**に飛ばす。死んでいく敵の横に線が着弾するのは、
当たっていてもバグに見える。

### FIREは4つ目の道具ではない

同じ丸が4つ並んでいて、どれが撃つのかを読む一瞬がある。
狙撃だけ**大きく・暖色**にした。どのシューターもそうしている場所に、その理由で。

## 6.12 「押し続けるのしんどい」——視点は戻さない

視点移動はボタンを離すとランナーへ戻る作りだった。
つまり**何かを見続けるには押し続けるしかない**。正当な苦情。

戻すのをやめた。オフセットはガーディアンが選んだ場所で、
カメラはランナーを追い続けるのだから、選んだオフセットはランナーと一緒に動く。
画面の後ろに何かが失われることはない。

さらに、**ボタンに触れたまま横に払うと視点がスクラブする**（2.2倍）。
長く見るのに3秒の押しっぱなしは要らず、一度の払いで済む。

戻すのは反対側のボタン、逆向きの払い、またはリトライ。

## 6.13 敵が「消えずに止まる」と「浮いている」は同じ1行だった

> 「倒したと思ったら敵が消えずに止まってる」
> 「キャラが地面から浮いているシーンが多すぎる」

別々の苦情に見えて、原因は1つ。**敵を「リストの何番目か」で識別していた。**

```gdscript
var id := 0
for e in get_tree().get_nodes_in_group("enemy"):
    ...
    id += 1
```

このリストは**1体死ぬたびに短くなる**。だから最初の撃破以降、
以降の敵の id が全部1つずつズレる。ガーディアンの端末は
**別の敵の座標に各敵を動かす**——歩行敵が飛行敵の高さに置かれ、草の上に浮く。

そして `ENEMY_DIE` は**音を鳴らすだけで、消していなかった**。
クライアント側の敵は自前の物理を止めてあるので、歩き去ることすらできない。
だから「止まったまま、消えない」。

**直し方：レベルデータ側の並び順で固定 id を振る。** データはどの端末でも
同じ順序で、誰が死んでも変わらない。`ENEMY_DIE` は id で引いて実際に消す。

負のコントロールで、位置ベースの id に戻すと39件、消さないようにすると1件落ちる。

**オフラインの接地は正常だった。** 測定できた歩行敵は -10px で、
木や看板と同じ（＝正しく座っている）。浮いて見えていたのは通信側のこのバグで、
スプライトの配置ではなかった。正直に言うと、接地プローブは
**動いている敵を6体измеりそこねたまま**で、そこは未解決の測定上の穴。

## 6.14 「別のシステムにして」への答え

> 「やはり射撃も足場もやりにくすぎる。別のシステム(3次元にするとか一人称にするとか)にして」

**3D・一人称にはしません。** 理由は規模ではなく、**それでは解決しないから**です。
親指で狙うのは2Dより3Dのほうが難しい。画面を回す操作が増えるぶん、
「狙う」というコストはむしろ上がります。

問題は次元ではなく、**システムが「座標」を要求していたこと**でした。

このゲームが求めている placement は、ほぼ全部が次のどれかです：

- 落ちているランナーの下に床
- ランナーと撃ってくる相手の間に壁
- ランナーに触れそうな敵に一発

**どれも座標の判断ではありません。** 判断は「どの道具を、いつ」であって、
それは**ボタンそのもの**です。

だから：**タップ＝「任せる」、ドラッグ＝「ここに」**。
`Guardian.auto_target(slot)` が、ガーディアンがどのみち出したはずの答えを出す
（落下速度を見越した先読み込み、最寄りの脅威との間、ランナーに最も近い敵）。
狙いたい場面のためにドラッグは残っている——**考えた配置だけが手間に見合う**。

これは次元を増やすより小さい変更で、しかも「狙う」という作業自体を
共通ケースから消している。

## 6.15 視点はボタンをやめて、画面を払う

> 「左右への移動はボタンじゃなくスクロールでやりたい」

同意。ボタンを押し続けるのは、地図を見るのに矢印キーを押し続けるのと同じ。

何もない所を指で横に払うとスクロールする。**26px 横に動いた時点で**
「これはスクロールだ」と確定し、それ未満なら照準の微調整のまま
（横移動が縦移動の1.4倍を超えることも条件——斜めの操作を誤解しないため）。

ボタン2つは**消した**。画面が静かになる。デスクトップのキーは残してある。

## 6.16 Cloudflare は無罪。合っていないのは「部屋」だった

> 「そんなに高難易度な通信ですか？失敗しすぎなので、原因を特定して別の方式に。
> 　cloudflareがだめなのかな？」

端末から届いた診断が、そのまま答えになっていた。

```
[1/4] GET /health   → HTTP 200
[2/4] POST /room    → HTTP 200
[3/4] WebSocket     → OPEN, {"t":"joined","role":"host","peers":1}
[4/4] ポート        → 開けました
いま動いている通信: ガーディアン側
  受信 0 個 / 送信 624 個
  相手がいるか: いいえ
```

**中継は4段とも通っている。** 壊れているのは通信ではなく**待ち合わせ**で、
この端末は部屋の中に**一人で座って624個の packet を虚空に送っていた**。

二人が別々の部屋で待っている状態は、**両方の画面で「壊れた中継」と見分けがつかない**。
これが「失敗しすぎ」の正体。

### 特定できるようにした

1. 診断が **★ この端末がいる部屋: XXXXXX** を出す。二人で見比べれば一発で分かる
2. 中継は参加順に役を割り当てるので、**ゲスト役が "host" を割り当てられたら
   その部屋は空だった**ということ。これは正確な検出なので、
   「この合言葉の部屋には、まだ誰もいません」と名指しで出す
3. 「表示の遅れ -62883ms」のような無意味な行を止めた
   （スナップショットが0件のとき、0から view_tick を引いていた）

### そして「別の方式」

**3段目までが通っているのだから、中継を別実装にしても何も直らない。**
直すべきは「合言葉を二台で一致させる」という手順そのもの。

> **【6.17で取り消し】** 以下の「同じWi-Fi」の経路は、頼まれていないのに
> 私の判断で足したもので、原因の読み違いから出ていた。実装ごと削除済み。
> 記録として残す。

同じWi-Fiなら、その手順は**要らない**。ホストが 0.6秒ごとに
`255.255.255.255:24681` へ「ここにいる」と言い、ゲストはそれを聞いて
**ボタンを1つ出す**。打ち込むものはゼロ、中継もインターネットも経由しない。
診断が「ポート24680は開けました」と言っているので、この経路は使える。

2プロセスで実測して、打ち込みゼロで相手を見つけることを確認済み
（負のコントロール：告知をやめると見つからない、期限切れを消さないと
消えたホストが残る）。

**正直な限界**：ルータによってはクライアント間のブロードキャストを
通さない（ゲストWi-Fiに多い「AP isolation」）。そのときは何も聞こえないので、
手入力のアドレス欄を残してある。

### ついでに：4.83秒

診断の1段目が **4.83秒**かかっている（こちらからは0.4秒）。
2段目は0.76秒、3段目は0.82秒なので、初回のDNS＋TLSの分。
壊れてはいないが、その回線が速くはないことの記録。
LAN経由ならこの数字は関係なくなる。

## 6.17 二台を並べて見るテストを、先に作った

> 「通信は成功。でも射撃に当たり判定がなかったり、壁ボタンを押しても別の位置に
> 　壁ができたり、ガーディアン側のキャラクターが点滅していたり……
> 　これは、ゲームシステムが難しすぎるということかな？」

**違う。難しいのは通信ではなく、私が自分の仕事を検証できていなかったこと。**

設計は最初から正しい（ホストが真実、ガーディアン端末は映すだけ）。
壊れていたのは実装で、報告された4件はどれも別々の書き間違いだった。
そして4件とも、**1121個のロジックテストには原理的に映らない**。
どのチェックも「1台のなかで正しいか」を見ていて、報告された不具合は
**2台を並べたときにだけ食い違う**ものだったから。

だから先にその物差しを作った（`test/agreement_probe.gd`）。

1. 実際のステージをホストとして走らせ、**送ったパケット**と
   **その瞬間に本当だったこと**を毎tick書き留める
2. その世界を捨て、新しい世界を建て、本物の `ClientSession` に
   さっきのパケットをそのまま流し込む
3. 毎フレーム「いま何tick目を描いているつもりか」を聞き、
   **描いている全部の位置**をその tick の真実と突き合わせる

ランナーを16か所に立たせて、20体中16体をガーディアンの画面に通す。
清浄な回線と、3%を落とす回線の両方で測る（前者で食い違えばコードの誤り、
後者との差が回線の代金）。カバレッジ自体もチェックしている——
**検査対象が空になったテストは永遠に通ってしまう**ので。

### 一度目の実行で、4件すべてが再現した

| 報告 | 実際の原因 | 実測 |
|---|---|---|
| 敵が浮いている／当たらない | リスポーンは `rebuild_dynamic()` で**全敵を作り直す**。`ClientSession._by_net_id` はハンドシェイク時の**一度きり**で作られるので、**最初の死亡以降は解放済みオブジェクト20個を指していた**。ホストの言うことは何にも届かず、新しい敵は物理が切られていないので**自前で動いて**ずれていく | 画面中央・ランナーから108pxの敵で**最大332pxの食い違い** |
| ガーディアン側のキャラが点滅 | 無敵時間を減らすのは `_tick_timers`、それが載っている `_physics_process` はガーディアン端末では切ってある。**誰も減らさない** | リスポーン後、**永久に点滅** |
| 壁が別の位置にできる | ゴーストは `_aim_world`、確定は `auto_target()`。**同じ問いへの答えが2つあった** | タップの着地点とゴーストが**620〜625px離れていた** |
| 射撃に当たり判定がない | パケットが**座標**しか運んでいなかった。その座標はガーディアンの画面のもので、ホストの敵はもう動いている。ホストは26px（補助110px）で照合する | 144px歩いた敵に対し、**名前なしの射撃は外れ、名前つきは当たる** |

修正は、順に：`Events.level_rebuilt` を建て直しのたびに上げて世界を取り直す／
puppet の `_process` で無敵時間を減らす／ゴーストと確定を `target_for()` 1本に統合する／
`Protocol.fire` に**撃つ相手の名前**を載せる（VERSION 2→3）。

**負のコントロールは4件とも取った。** 各修正を元に戻すと、
それが守っているチェックだけが落ちる（敵12/17体、点滅、ゴースト620px、名指し射撃）。

### 6.16 の「同じWi-Fi」は取り消した

> 「WiFiが同じ場合の参加方法も不要」

そのとおり。あれは**誰にも頼まれていない**。私が接続不良の原因を読み違えて
自分で足したもので、原因は別のところにあった。結果として
「はじめての画面」に**同じゲームの始め方が3つ**並び、うち2つは同じ部屋にいる
ときしか動かなかった。ビーコン、発見リスト、IPアドレス欄、診断の4段目——全部消した。
残したのは「1台で2人」と「合言葉で入る」の2つ。合言葉のほうは同じ部屋でも動く。

## 6.18 「自動配置」を消した。ボタンは選ぶのではなく確定する

> 「足場ボタンや壁ボタンを押しても、タップした位置ではなく全く違う位置にできてしまう」
> 「足場・壁は自動配置をやめ、指定した位置をそのまま使うように直す必要があります。
> 　プレビューと実際の配置も、その同じ座標を使うべきです」

**指摘のとおりで、しかも `guardian.gd` の読み方まで正確だった。** 直した。

6.9 でこう書いた——「狙いが難しいなら、狙わせるのをやめる。ほぼ全ての配置は
決まりきった数個のどれかで、決定はどの道具かであって、座標ではない」。
この理屈は**間違っていた**。しかも一番まずい間違い方をしていた：
**プレイヤーが既に指したった場所を、黙って書き換えていた。**

「壁ボタンを押すと全然違う所に壁ができる」は、ルールが少しズレているという
報告ではない。**そのコントロールが信用できない**という報告。

ルールは1つになった：**指した所に置く。**タップでもドラッグでも、
どの道具でも、ゴーストでも。「置きたい場所をタップ → 道具のボタンを押す」で
そのまま置ける（ドラッグのときだけ、指で隠れないよう上にずらす補正が残る）。
`auto_target` / `_catch_point` / `_shield_point` / `_nearest_threat` は削除。

ライフルも同じにした。指摘は足場と壁についてだったが、**同じ驚きが起きる**ので
揃えた。外す精度の担保はホスト側の110px補助が引き受けている。

### 接続：再起動しないと入れなかった理由

> 「ゲーム開き直してからまた部屋作ると入れた」
> 「古い接続やセッションの残留かもしれない。普通のゲームでこんなこと起こる
> 　はずないので、絶対に避けてほしい」

**残留で合っていた。3つ重なっていた。**

1. **`_become_host` / `_become_client` が前のセッションを片付けていなかった。**
   参加に失敗しても `ClientSession` は生き残り、死んだソケットを polling し続け、
   `guardian.command_router` も握ったまま。そこで「部屋を作る」を押すと
   `HostSession` が**隣に増える**。セッション2つ、transport 2つ、
   `Clock.is_host` は後から `_ready` した方が決める。
   アプリを終了するしか消す手段がなかった。
2. **開かなかったソケットを、誰も掛け直さなかった。** 6.12 で入れた
   「最初の1個が来る前の沈黙は切断ではない」という規則を、
   **自分の回線が開いていない場合にまで広げてしまっていた**。
   端末から届いた記録がそれそのもの：`部屋 5QK2TN / 受信 0 / 送信 0 / 接続: 閉じています`。
   いまは「自分のリンクが開いているか」で分ける。開いていなければ掛け直す。
3. **最初の poll より前に死んだソケットは、失敗を報告しなかった。**
   `_state` の初期値が `STATE_CLOSED`（実在する状態）だったので、
   「変化なし」に見えて `failed` が出ない。接続画面は
   「部屋 XXXXXX につないでいます…」のまま**永遠に**止まる。初期値を -1 にした。

### 診断が間違った答えを出していた

同じ記録で、診断は「**この端末は部屋にいますが、相手がいません**」と言い、
合言葉を1文字ずつ見比べろと指示した。**部屋に入れてすらいなかった。**
`packets_in == 0` だけを見て結論していたため。いまはリンクが開いているかで
分岐する。ついでに [3/3] が [2/3] で作った部屋ではなく自前の新しいコードを
試していたのも直した（経路全体の証明になっていなかった）。

負のコントロール：3つとも、戻すとそれが守るチェックだけが落ちる
（配置622pxズレ・掛け直し0回・セッション残留4件）。

## 6.19 浮いていたのは体ではなく、影と着地ポーズだった

> 「ジャンプ後着地するとキャラクターが浮くことがある現象はどうしても避けられない
> 　ものですよね？もう、浮くのは私たちの技術的に不可避だと諦めるので、
> 　浮いていたら高速で地面に下ろす処理を出して」

**不可避ではなかったし、物理でもなかった。** 頼まれた「下ろす処理」は、
入れても**何も起きなかった**ところだった。

### まず測った

`test/landing_probe.gd`：ステージ上の9か所でジャンプさせ、着地直後と落ち着いた後に、
足の裏から真下へレイを飛ばして隙間を測る。

```
18回の着地  平均 0.02px  最大 0.03px
1.5px より浮いていたもの: 0 / 18
```

**体は地面に付いている。** `floor_snap_length = 8.0` が効いている。
ポーズ画像8枚も全部キャンバス下端に接していた（下パディング 0px）。

### では何が浮いて見えるのか

接地の**描画**が、`is_on_floor()` を読んでいた。

`is_on_floor()` は直前の `move_and_slide()` の結果で、**ガーディアン端末では
その物理を切ってある**。つまり世界を引き取った瞬間の答えのまま固まって、二度と
変わらない。それに乗っているのが：

- **接地影** — 空中では小さく薄くなる。固まると、着地しても空中用の影のまま
- **着地しゃがみポーズ** — `_squash` が発火せず、一度も出ない

**影が地面から離れて小さいままなら、キャラは浮いて見える。** それが正体で、
点滅（6.17）とまったく同じ種類のバグだった——「物理が動いている前提の値を、
物理を止めた端末で読んでいる」。

`Runner.grounded` を足して、ホストは自分の物理から、ゲストは**すでに送っていた
スナップショットの1ビット**から設定する。描画は `on_ground()` を読む。
負のコントロール：ゲストへの通知をやめると、立っている判定が2つ落ちる。

### 頼まれた「下ろす処理」も入れた

測った限り発火しないが、ジャンプテストが届かない場面はある——足元の構造物が
消える、足場が動いて外れる、崩れる床。`_hug_the_ground()` として入れた。
接地していた直後（0.2秒以内）かつ下降中のときだけ `apply_floor_snap()` を呼ぶ。
この窓がないと、**崖から踏み出した1フレーム目を掴んで縁に貼り付ける**。

## 6.20 足場をタップすると、乗っている人が飛ぶ

> 「足場を神側がタップしたら、キャラがバネのように飛ぶようにしてください」

どちらの意味か確認したうえで実装：**すでにある足場をタップして発射**、
**自力ジャンプの約2倍**。

ガーディアンにとって初めての「**置く**以外の動詞」になる。ボタンもゲージも要らず、
**タップしたものが動く**ので因果が一目で分かる。

条件は2つとも要る：タップ位置に足場があること、**ランナーがその足場に乗っている**こと。
乗っていない足場をタップしても何も起きない——そうでないと「どこからでも発射できる
ボタン」が足場の皮をかぶっているだけになる。

高さは `PLATFORM_LAUNCH_VELOCITY = -880`。h = v²/2g なので約256px、
自力ジャンプ（128px）のちょうど2倍。**数値1つ**で変えられる。

オンラインでは予測しない。ランナーはホストのもので、飛ばしてから「やっぱり無し」と
取り消すのは、1往復待つより悪い。`Protocol.Msg.LAUNCH`（VERSION 3→4）。

### ついでに見つかった：タップ判定が斜めにしか効いていなかった

タップとドラッグを分けるのに指の移動量を見るのだが、`_aim_from` は**原点ではなく
前フレームの位置**で、毎回上書きされている。さらに照準は20Hzに間引いてある。
どちらも「この指は動いたか」に答えられない。真上へのドラッグが**タップとして
通ってしまい**、照準を上に動かすたびにランナーが打ち上がるところだった。
移動量を累積するようにした（`_aim_moved`）。

## 6.7 つながらなかった理由（自分で入れたバグ）

> 「同じwifiでも、遠隔でも接続できずゲーム始められません」

中継サーバー（Cloudflare Worker）は生きていた。ここから実際に叩いて確認済み：
`/health` が 200、`POST /room` が部屋を作り、WebSocket 2本が open して
バイナリもテキストも相互に届く。**サーバーは無罪。**

### 原因：6.6 の「再接続」が、まだ接続していない接続を切っていた

`ClientSession._watch_link` は「4秒無音なら切断」と判断する。
これは**一度つながった後**なら正しい。しかし**最初の1パケットが来る前**の沈黙は
切断ではなく、相手がまだ合言葉を読み上げている時間である。
6文字を口で伝えるのに4秒以上かかるのは毎回のことだ。

結果：参加側は**一度も繋がる前に「切れた」と判断して再ダイヤルを始める**。
そして中継の部屋は**2人しか入れない**ので、古いソケットが生きたまま
2本目を張ると `room is full` で弾かれる。つまり**リトライも失敗し続ける**。
90秒後に `disconnected` を出して `set_process(false)`——完全に死ぬ。

同じWi-Fi（ENet）でも同じ `ClientSession` を通るので、両方壊れていた。

**直し方**：`_ever_heard` を持ち、一度も何も届いていない間は監視を始めない。
**一度も成立していない接続は、再接続できない。待つことしかできない。**
併せて `WebSocketTransport.reconnect()` は再ダイヤル前に古いソケットを閉じる。

再現テスト `_test_a_slow_start_is_not_a_drop` を先に書いて落ちることを確認し、
直してから通した（負のコントロールも確認済み）。

### ついでに塞いだ穴：拒否された握手が誰にも見えない

接続画面は「中継が"2人揃った"と言った時点」で閉じていた。
ところがビルド不一致の拒否は**その後**の握手で起きる。
拒否メッセージは HUD に 1.1 秒だけ流れ、その下には
**絶対に始まらないゲーム**が表示されていた。

参加側は `handshaken`（ホストからの WELCOME）を待って閉じるようにした。
ホスト側はランナーの端末＝ゲーム本体なので、相手が部屋に入った時点で閉じてよい。

### 恒久的な答え：端末上で全工程を試す診断

原因が「私のバグ」だったのは今回の話で、次は回線かもしれない。
`src/ui/net_diagnostics.gd` は接続の全工程を**その端末で実際に実行**し、
各行にタイムスタンプ・結果・所要時間を書く。

| 段 | 見るもの | これで切り分くもの |
|---|---|---|
| 1/4 | `GET /health` | そもそも外に出られるか |
| 2/4 | `POST /room` | サーバーが動いているか |
| 3/4 | WebSocket upgrade | **HTTPは通すのにWebSocketを落とす回線**（社内・学校・ホテル） |
| 4/4 | ENetのポート bind | 同じWi-Fiのホストになれるか |

所要時間を必ず書くのは、**DNS失敗と遮断が「失敗」としては同じに見えて、
20ms と 10秒という違いで見分けられる**から。
出力は読み取り専用 `TextEdit` に入れ、「すべてコピー」で
`DisplayServer.clipboard_set()` に渡す——貼って送れることが目的なので。

## 6.6 品質を底上げした3点（音・切断・採点）

遊べる状態から「作品」に寄せるとき、何から手を付けるかを順番に並べて上から3つ。

### 音を「ゲーム側から呼ばない」構造にした

`Audio` オートロードは **イベントバスだけ**に繋がっている。ゲームのスクリプトは
どれ一つとして `Audio.play()` を呼ばない。イベントは「何が誰に起きたか」を既に
表現しているので、音はその購読者の一つで足りる——ゲームのロジックを二重に持たない。
音を止めたければこのノードを外せばよい。

副作用として**ガーディアン側でも同じ音が鳴る**。ガーディアンの端末は何も
シミュレートしていないが、ホストから中継された出来事と、受け取ったスナップショットから
復元した動き（ジャンプ・着地）でイベントを立てているので、同じ購読者が同じ音を鳴らす。

**この作業中に見つかった別の不具合。** ホストは `shot_fired` / `enemy_killed` /
`switch_activated` を**自分のバスにしか立てていなかった**。音を付けようとして
初めて気付いた：オンラインのガーディアンは、自分が撃った曳光弾も、敵が消える瞬間も、
扉が開く瞬間も**見えていなかった**。`WORLD` メッセージを足して中継するようにした。
音という「別の購読者」を足したことが、既存の穴を見つける検査になった形。

音そのものは**合成**（`tools/make_audio.py`、numpy で波形生成→16bit WAV）。
ループの継ぎ目は、末尾にはみ出した音符を**切り捨てず先頭に巻き戻して**加算している。
継ぎ目の1サンプル差 0.0000 に対し、内部の平均サンプル間差 0.0100 で、段差はない。

### 切断を「終わり」ではなく「待ち」にした

モバイルでは切断が普通に起きる（裏に回す、Wi-Fi↔LTE、電波の谷）。
これまではそこでセッションが終わっていた。

- 4秒なにも届かなければ切断とみなす（`SILENCE_IS_A_DROP`）
- 2秒おきに同じ部屋へ入り直す（`RETRY_EVERY`）、90秒であきらめる（`GIVE_UP_AFTER`）
- **戻ったらバッファを捨てる。** 古いスナップショットを補間すると、
  ランナーが一度過去に引き戻されてから現在に飛ぶ
- ホストは `HELLO` を受けるたびに**取りこぼしを送り直す**
  （生存している足場・壁・ワープ、開いたスイッチ）

最後の1点は、テストが**嘘をついた**ところでもある。最初のテストは再送内容を
手で送り込んでいたので、`_resync()` を丸ごと消しても通った。実物の `HostSession` を
動かすテストに差し替えたら、負のコントロールが正しく2チェック落ちた。

### ガーディアンの「うまさ」を画面に出した

ここまで、ぎりぎりで受け止めても余裕で置いても**ゲームは何も言わなかった**。
落下中のランナーを受け止めたとき、**置いてから踏まれるまでの時間**で採点する。

| 評価 | 猶予 | 還元 |
|---|---|---|
| PERFECT! | 0.35s | +24 |
| GREAT! | 0.8s | +14 |
| NICE! | 1.6s | +6 |

還元をゲージにしたのは、上手さが**次の一手**に変わるため。得点だけなら数字が
増えるだけで、遊びは変わらない。落下速度 420px/秒 未満は対象外——置きっぱなしの
足場に乗るのは「受け止め」ではない。

**採点は `placed_tick` で行い、`birth_tick` では行わない。** ホストは遅延補償で
構造物の誕生時刻を過去にずらす（`HostSession._do_place`）。これを採点に使うと、
**回線の悪いガーディアンほど評価が下がる**——ホストが既に許した遅延の分を、
評価で二重に取り立てることになる。テストは 1.5 秒分バックデートした構造物が
NICE ではなく PERFECT になることを確認していて、採点対象を `birth_tick` に
戻すとそのチェックが落ちる。

検証は**実際の落下**で行っている。落とす高さと足場までの距離を変えて3段階を作り、
着地時に構造物が到達していた実測年齢と、出た評価の両方を突き合わせる。

## 8. 役割交換について

企画書 7 章は「チェックポイントで任意交換」としているが、本実装では
`Tab`（モバイルでは今後ボタン化）でいつでも交換できるようにした。
1 台共有では交換＝物理的に座る位置を入れ替えることなので、ゲーム側が
タイミングを縛る必要がない。ゲームがやることはタッチ配置の左右反転だけで、
`TouchLayout.flip_x()` がそれを担っている。
