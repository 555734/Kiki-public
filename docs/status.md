## 1. これは何か

**非対称協力プレイの2Dアクション。** 2人で1つのステージを進みます。

| 役 | できること |
|---|---|
| **ランナー（LIRA）** | 移動・ジャンプ・スプリント・空中ダッシュ。敵に触れれば上からでも被弾する（倒すのはガーディアンの狙撃） |
| **ガーディアン（神視点）** | 足場を置く／壁を置く／狙撃する／ワープ門を置く。**そして足場をタップして、乗っている人を打ち上げる** |

ランナーは自分の周りしか見えず、ガーディアンは先が見えます。
**ランナー単独では越えられない場所が用意してあり**、そこがこのゲームの会話になります。

想定端末は **iOS / Android**（ブラウザ版はありません）。横持ち。

### ガーディアンの道具

| | コスト | 効果 |
|---|---|---|
| 足場 | ゲージ | 一定時間で消える床。数に上限あり |
| 壁 | ゲージ | 弾とレーザーを止める盾 |
| 狙撃 | ゲージ＋クールダウン | 敵とスイッチを撃つ。照準から110pxまで自動補助 |
| ワープ門 | ゲージ | 2つ置くと繋がる |

**すべて「指した所」に出ます。**置きたい場所をタップ → 道具のボタンを押す。
ボタンから指を引き出して離してもかまいません。どちらでも同じ場所で、
**ゴーストが出ている所が必ず出る所**です。

### 操作

丸ボタン式。**位置もサイズもプレイヤーが自由に変えられます**（接続画面の
「ボタンの位置を変える」から）。左右に振り分けた既定配置つき。
ガーディアンは画面を払って視界を左右にスクロールできます（ランナーから一定範囲内）。

**自動ダッシュ**（設定で切り替え）。押しっぱなしのダッシュは電話では指が2本必要で、
ジャンプがその1本を欲しがります。有効にすると移動しているだけで走ります。

代償は**停止距離**です。常に最高速度で走っている人は止まるのに長くかかり、
それが効くのは狭い場所です。だから 1-T の1ブロック幅の足場で、
**有効にしても1ブロック以内で止まれること**を測っています（16px → 10px）。

### 音

29種類の効果音。すべて**合成音**です（録音素材ではありません）。
ジャンプ、着地、ダッシュ、被弾、コイン、バネ、狙撃、着弾、敵の撃破、
足場の生成と消滅、チェックポイント、ゲームオーバー、カウントダウンなど。

### オンライン

**ランナーの端末がシミュレーションを持ちます**（ホスト）。ガーディアンの端末は
**何もシミュレーションせず、送られてきた世界を映すだけ**です。
これは普通のオンラインゲームと同じ作りで、設計自体は最初から正しく動いています。

- 中継は Cloudflare Worker + Durable Object
- スナップショット 30Hz、13バイト（近くの敵1体につき +6バイト）
- 補間はエルミート（ジャンプの頂点が潰れないように）
- 移動床とレーザーは**tickの関数**なので、1バイトも送っていません
- ガーディアンの操作はホスト側で**時間を巻き戻して**判定します（回線が悪い人が損をしないように）

## 3. 遊び方

接続画面の選択肢は**2つだけ**です。

1. **1台で2人であそぶ** — 画面を左右に分けて2人で持つ

## 4. 検証の仕組み

**このプロジェクトで一番重要な部分です。** 実機が手元にないので、
検証できる範囲の広さがそのまま品質の上限になります。

`tools/verify.sh` が8段階を回します。合計 **1,536チェック**。
別に `tools/duet.sh` が、2プロセス＋本物の中継で **41チェック**（ランナー側19・神側22。下の「2台を本当に動かす検証」）。

| 段 | 何を守っているか |
|---|---|
| 1. インポート | クラス名の解決。ここが崩れると以降が全部無意味になる |
| 2. 全スクリプト解析 | **構文エラーのあるシーンは無言でハングする。**だから最初に通す |
| 3. ロジックテスト | **1,439チェック。**ルール・物理・ネットコード・入力・座席 |
| 4. 着地の実測 | ジャンプ9か所×2回、足の裏から真下へレイを飛ばして隙間を測る |
| 5. **端末間の一致** | **23チェック。**下に説明 |
| 6. **平地でない形** | **28チェック。**継ぎ目・段差・角・低い天井・移動床（1-T） |
| 7. **1-Cを二人で通す** | **41チェック。**下に説明 |
| 8. 実ステージの起動 | 実際に240フレーム動かす |

2台検証は別立てです（中継サーバーを立てるので、通常の `verify.sh` には入れていません）:

```
tools/duet.sh              # 中継を起動し、ゲームを2つ起動して突き合わせる
```

`--shots` を付けると、さらに実画面（xvfb）で3つ走ります —
接続画面の実タッチ操作、全スプライトの接地のピクセル計測、スクリーンショット撮影。

### 「端末間の一致」テストが一番効いています

実機から報告された不具合は**全部ガーディアン側**で、そして**1,139個のロジック
テストには原理的に映りませんでした**。どのチェックも「1台のなかで正しいか」を
見ていて、報告された不具合は**2台を並べたときにだけ食い違う**ものだったからです。

そこで `test/agreement_probe.gd` を作りました。

1. 実際のステージをホストとして走らせ、**送ったパケット**と**その瞬間に本当だったこと**を毎tick記録
2. その世界を捨て、新しい世界を建て、本物の `ClientSession` にそのパケットを流し込む
3. 毎フレーム「いま何tick目を描いているつもりか」を聞き、**描いている全部の位置**を真実と突き合わせる

ランナーを16か所に立たせ、20体中16体の敵をガーディアンの画面に通します。
清浄な回線と3%落ちる回線の両方。死亡→リスポーン後も。
**カバレッジ自体もチェック対象**です（検査対象が空になったテストは永遠に通るので）。

### ステージは「遊べるか」を毎回測り直します

`test/stage_probe.gd` は 1-C を6節とも**実際に遊びます。**ガーディアンが道具を
選んでタップし、ランナーが走って跳んで、蹴って、撃たれて飛ぶ。
どこかの節が通れなくなったら、その節の名前で落ちます。

そして寸法の前提を**モデルではなく実測**にしています。最初は射出の飛距離を
重力の式で出して561pxとしていました。ランナー本人に飛ばせたら**349px**でした。
式が空中制御を含んでいなかったからです。この差が、下の「射出が跳躍より飛ばない」
という不具合そのものを掘り当てました。

### 平地では何も分からない（1-T「THE WORKSHOP」）

`balance.gd` の数値は全部**平らな地面で**決めて、全部**平らな地面で**測っていました。
そして平地は、**横スクロールが唯一失敗できない場所**です。台地では完璧に感じるのに
足場の継ぎ目で引っかかるランナーは誰にも信用されませんし、ジャンプの弧をいくら
測っても分かりません — 弧は正しいので。

そこで 1-T を作りました。遊ぶためのステージではなく、**測るための部屋**です。
気持ち悪さを生む形だけを一列に並べ、間に平地を置いて1つずつ踏みに行けるように
してあります。

| 形 | 何を訊いているか |
|---|---|
| 継ぎ目 | 同じ高さの2枚が接する所。見た目は何も無く、判定が1px違えば何も無い所でつまずく |
| 1ブロックの段差（上／下） | 歩いて当たったとき。登るか止まるかはどちらでもよいが、足首の高さで止まったまま走るモーションは駄目 |
| 1ブロック幅の足場 | 乗れるかと、**止まれるか**。答えは停止距離という名のつまみ |
| 低い天井 | 上昇が天井で終わるか。吸着せず、横に飛ばされず |
| 廊下（低い天井＋継ぎ目） | 別々なら平気でも、重なると引っかかる所 |
| 外側の角 | 崖の猶予が**ある**ことと、**終わりがある**こと |
| 内側の角 | 床と壁の合わせ目。登らず、貼り付かず、震えず |
| 移動床 | 乗って運ばれるか、そこから跳べるか |
| 計測直線 | ジャンプ高と頂点までの時間を、この同じステージで測る |

`test/workshop_probe.gd` が**28チェック**、形ごとに名前を付けて落ちます。

### 2台を本当に動かす検証（新規）

`tools/duet.sh` は**ゲームを2プロセス起動**し、本物の中継サーバーを挟んで、
片方をランナーの端末、もう片方を神の端末として遊ばせます。

他の全テストは1プロセスの中で動きます。それは録画→再生→突き合わせという形には
正しいのですが、**「2人がそれぞれ自分のボタンを押したとき同じゲームが起きるか」**
だけは答えられません。1プロセスは自分自身とは必ず一致するからです。

- どちらのプロセスも、相手が何をしているかを教えられていません。**世界を見て合わせます**
- 神の操作はすべて**タッチ**から入ります（指→画面→ワールド→パケット→ホスト判定→両方の画面）
- 食い違いは「片方だけ落ちる」という形で出ます

通しているもの（ランナー側17・神側22）：接続と役割 ／ タップした所に足場が出る
（**ずれ0.00px**）／ ボタンを押しただけでは何も建たない ／ 射出足場に乗って撃たれて
**745px**飛ぶ ／ 壁を蹴る ／ 結晶が1回だけ数えられ神のゲージになる ／
盾は弾を止め、開き口は止めない ／ 取り消しは返金しない ／
**回線が切れて、自力で戻り、同じ世界が返ってくる**（結晶8個そのまま）

これで見つかった不具合は2つ、どちらも**神側だけで起きるもの**でした。

**① 射出済みの足場が、神の画面では光ったままだった。**
ホストは `armed=false` にしますが、それを伝える口がありませんでした。
「乗っている／撃てる」が両方に見えることが、声を出さずに呼吸を合わせられる理由なので、
そこが嘘をつくと二人は動かない足場を前提に作戦を立てます。

**② 盾持ち敵の弱点が、神の端末では敵の真ん中に埋まっていた。**
盾と弱点の位置は `_physics_process` の中で更新していました。
神の端末では敵はスナップショットで動く人形なので、その処理は**切ってあります**。
結果、**絵では盾と弱点が左右に描かれているのに、当たり判定は両方とも中央に重なって**
いて、ランナーが作った開き口を狙った弾はすべて盾に吸われました。
**神側からはこの敵は一度も倒せませんでした。**位置の計算はランナーの座標しか
使わないので、両方の端末で回すようにしました。

なお、この検証が見ているのは「倒せたか」ではなく**仕組みそのもの**です
（盾は弾を止める／ランナーが作った開き口は止めない）。1体倒すのに射撃2発＝ゲージ40、
回復は毎秒8なので、「2発目が何秒以内に入るか」は経済とプロセスの速度の話になり、
実行ごとに結果が変わって何も分かりませんでした。敵のHPはスナップショットに
入っていない（＝神側は数字を見られない）ので、**HPの判定はランナー側の端末**に
置いてあります。

### 検証中に見えた操作上の事実

盾持ち敵の弱点のように**画面の下のほうにある的**は、能力ボタンの帯の真下に
入ることがあります。そこを普通にタップすると、それは「道具を選ぶ」操作として
解釈されます（この設計はそのとおりで、ボタンの上は必ずボタンです）。

ゲーム側には答えが2つ用意されています — **視点を動かしてからタップする**か、
**ボタンから指を引き出して離す**か。2台検証はこれを踏んで、
「撃ったのに何も起きない」が5回続きました（実際には道具がワープ門に
切り替わっていました）。検証側を「的がボタンの下にあるなら先に視点を動かす」
という、人がやるとおりの手順に直しました。

### 「テストが黙って途中で終わる」問題

GDScript では、`await` で待っている関数の中で実行時エラーが起きると、
**その関数は何も落とさずに打ち切られます。**残りのチェックは走らないだけで、
集計は「全部通った」と言います。

このプロジェクトで3回踏みました。直近は2台検証で、**4秒で消える壁の参照を
握ったまま次の試行に入り**、解放済みノードを読んだ瞬間にランナー側の
スクリプトが9チェックで打ち切られ、`PASS` と表示されました。
（そして神側は「ホストが応答しない」で落ち、原因が別の場所にあるように見えました。）

いまは**最後の行まで到達したことを1つのチェック**にしてあります。
到達していなければ、そう言って落ちます。

### 負のコントロール

**新しいチェックを入れたら、必ずそれが守っているものを壊して、落ちることを確認します。**
落ちなければ、そのチェックは何も守っていません。この習慣が、実機バグの原因特定を
推測から測定に変えました。

### 第2段階：絵を入れる

同じ光源から合成。ランナーは8ポーズ。発光・落ち影・パーティクル・
ヒットストップ・本物のフォント。

### 第3段階：配布経路を通す

**GitHub Actions が private リポジトリで動かなかった**（毎回3秒で殺される）ため、
Codemagic に移行。Android は APK 2本を `dist/` に直接コミット。
iOS は署名まわりで長く詰まりました — Apple の配布証明書は**作った端末にしか
秘密鍵がない**ので既存のものが使えず、CIで鍵を生成する形に。
失敗のたびに証明書スロットを埋めるループも踏みました。

### 第4段階：実機で遊んで、壊れているところを直す（09-11〜12）

**ここが一番長く、一番学びがありました。** 実機から上がってきた不具合は
すべてガーディアン側の通信経路にあり、そしてどれも私の書き間違いでした。

流れ：

1. 「ラグが0.5秒ある」「10秒で切れる」 → クロックがゲスト側で進んでいなかった
2. 「ボタン操作が多すぎる」 → 道具ごとにボタンを分け、丸ボタンを親指の届く位置に、位置とサイズを変更可能に
3. 「敵に当たっても倒せない」「倒しても消えない」 → 敵のIDが配列の位置だった（死ぬたびに全部ずれる）
4. 「cloudflareがだめなのか」 → 中継は無罪。**二人が別々の部屋にいた**のを見分けられていなかった
5. **「これは難しすぎるということ？」** → いいえ。難しいのは通信ではなく、**私が自分の仕事を検証できていなかったこと**。ここで端末間一致テストを先に作った
6. 「壁ボタンを押しても別の位置に壁ができる」 → **自動配置を全部消した**（→ 6章）
7. 「着地すると浮く」 → 物理ではなかった（→ 6章）

### 第5段階：二人でしか越えられないステージを1本作る（09-12）

ここまでの 1-1 は、上手いランナーなら1人でも押し通れました。それは
「その場で作戦を考え、互いを助ける」体験にならない、という指摘のとおりです。

そこで 1-C を作り、**各セクションに1人では答えのないものを1つずつ**置きました。
そして通せるかどうかを、`test/stage_probe.gd` に**毎回実際に遊ばせて**います。

この過程で、**射出が跳躍より飛ばない**という重大な設計バグが出ました
（→ 6章の表の最終行）。テストがなければ、実機で「なんか弱い」としか
分からなかったはずのものです。

あわせて「プレイヤーID・役割・チームID」を別々のものとして持つようにしました
(`src/net/party.gd`)。いまは2人・1チームなので3つは常に一致しますが、
**一致しているうちに分けておかないと後で分けられません。**
将来のチーム戦のための土台で、サーバーは作っていません。

そして最後に、**2プロセスで本当に2台動かす検証**を入れました（→ 4章）。
ここでも2つ出ました。どちらも**神の端末でだけ壊れていた**もので、
1台のテストを何個増やしても見えないものです：
**射出済みの足場が光ったまま**、**盾持ち敵の弱点が敵の中央に埋まっていた**。

もう1つ、テスト環境そのものの発見もありました。1台の機械でゲームを2つ起動すると
`user://` を共有するので**2つが同じ端末IDを名乗り**、中継サーバーは正しく
「同じ人が戻ってきた」と判断して先にいた方のソケットを切ります。二人が延々と
蹴り合って、画面には理由が出ません。実機では起きませんが、**バックアップを復元した
端末どうしでは起こりえます。**端末IDを言える・変えられるようにしておきました
(`--client-id`)。

## 6. 直近で直した実機バグ

すべて**実測値つき**、すべて**負のコントロール済み**です。

| 報告 | 本当の原因 | 実測 |
|---|---|---|
| 敵が浮く・撃っても当たらない | リスポーンは全敵を作り直す。ガーディアン端末はハンドシェイク時の**一度きり**で敵を記録していたので、最初の死亡以降は**解放済みオブジェクト20個**を指していた。ホストの言うことが届かず、新しい敵は物理が切れていないので自前で動いてずれる | 画面中央・ランナーから108pxの敵で**332pxの食い違い** |
| キャラが点滅し続ける | 無敵時間を減らす処理が、ガーディアン端末では切ってある物理の中にあった | リスポーン後**永久に点滅** |
| 壁が別の位置にできる | ゴーストは指の位置、確定は自動配置。**同じ問いへの答えが2つ**あった | **620px離れていた** |
| 射撃に当たり判定がない | パケットが**座標しか運んでいなかった**。それはガーディアンの画面の座標で、ホストの敵はもう動いている（照合は26px、補助110px） | 144px歩いた敵に、名前なしは外れ／名前つきは当たる |
| 再起動しないと部屋に入れない | ①前のセッションが片付けられていなかった ②開かなかったソケットを誰も掛け直さなかった ③最初のpollより前に死んだソケットが失敗を報告しなかった | 記録上 `受信0 / 送信0 / 接続: 閉じています` |
| 着地すると浮く | **物理ではなかった。**接地の**描画**（影・着地しゃがみ）が、ガーディアン端末では止まっている物理クエリを読んでいた | 体の隙間は18回の着地で**平均0.02px** |
| （報告前に発見）射出が弱い | **足場から撃ち出された勢いが1フレームで消えていた。**空中制御が横速度を歩き速度へ引き戻すので、ガーディアンのゲージを使い二人で段取りした技が、**1人がボタンを2つ押すより飛ばなかった** | 射出**349px** 対 1人の跳躍**326px**。直して**679px** |
| （同上）その直し方が効いていなかった | 「射出中は減速しない」を入れたのに、`is_on_floor()` が**撃たれたフレームではまだ真**なので、次のフレームで印が消えていた | 空中で測ると679px、足場から撃つと**170px** |
| （報告前に発見）神側から盾持ち敵が倒せない | **盾と弱点の当たり判定が、神の端末では敵の中央に重なっていた。**位置を更新する処理が、神側では切ってある物理の中にあった。絵は正しく左右に描かれるので、見えている開き口を撃っているのに全部盾に当たる | 2台検証で**弱点への射撃6発すべて無効**。直して2発で撃破 |
| （報告前に発見）射出済みの足場が神側では光ったまま | ホストは使用済みにするが、**伝える口がなかった** | 2台検証で `armed` がホスト false / 神 true |

### コードレビューで指摘された4件（すべて再現→修正→負のコントロール）

| 指摘 | 本当の原因 | 直し方 |
|---|---|---|
| 中継URLを保存すると端末IDが消える | 保存側が**新しい ConfigFile を作って**キー1個だけ書いていた。同じファイルに入っている端末IDが道連れになる。次回起動時、中継サーバーから見て**初めて見る端末**になり、再接続を「戻ってきた人」と認識できない | 設定ファイルの持ち主を `NetLink` 一箇所にし、**読んでから1キーだけ書く** |
| 再接続で足場が重複し、使用済み発射台が戻らない | 復元が「生成イベントの再送」だった。イベントは**足すことしかできない** — 消えた物を消せず、位置を直せず、切断中に使われた発射台を伝えられない。神側は自分の足場を捨てていないので**毎回倍になる** | **状態**を1通で送る（`HOLO_LIST`）。無い物を消し、有る物を更新し、足りない物を足す。使用済みフラグも運ぶ。復元完了まで設置を止める |
| ランナーの誘導なしで盾敵を倒せる | 弱点が開く条件が「回転中でない」＝**既定で開いている**。誰もいない敵を神が背後から撃てば終わり。二人必要な敵が**一人も必要としていなかった** | 開く条件を「**ランナーが向きを変えさせた直後の短い時間**」に変更。判定はホスト、有効期限を両端末へ配る |
| 指を離した位置が設置に渡らない | リリースイベントは座標を持っているのに `_touch_up(index)` が**捨てていた**。確定は共有の照準（＝最後のドラッグ位置）を読む。ゆっくり動かせば一致するが、素早く動かすと**指が止まった所より手前**に出る | 指IDごとに最終位置を持ち、**リリースイベントの座標**で確定する |

### 操作感の調整：ジャンプを「高さと時間」から決める

重力の数値を選んでも、どんなジャンプになるかは分かりません。**どの高さまで、
何秒で届くか**を選べば、それを作る重力と初速はちょうど1組に決まります。

```
重力 = 2H / T²        初速 = 2H / T
```

`balance.gd` の先頭に、この2つを含む「つまみ」だけを集めました。ブロック幅 B を
単位にして、速度も加速も**時間と距離で**書いてあります。

| つまみ | 値 | 実測 |
|---|---|---|
| 長押しジャンプの高さ | 3.2B | **161px（3.36B）** |
| 頂点までの時間 | 0.33秒 | **0.333秒** |
| 短押し | — | 長押しの**53%** |
| 通常移動 | 5.7B/秒 | 走り幅 151px |
| ダッシュ | 8.6B/秒 | 走り幅 **248px** |
| 崖の猶予／先行入力 | 0.08／0.10秒 | — |

**これを変えた瞬間に、速度で書いてあった物が全部壊れました。**バネの打ち上げが
270px→144px、壁蹴りの上昇が112px→60px、崖つかまりの判定窓が6フレーム→4フレームに
なって誰も掴めなくなり、**射出足場が679px→374px**（＝1人のジャンプ333pxとほぼ同じ）。
どれも、そのコードには誰も触っていません。

**速度は、重力を知らなければ距離ではない。**だから全部「高さ」と「距離」に
書き換えました。バネ、壁蹴り、崖つかまりの窓、射出 — いまはどれも重力から逆算します。

そしてステージ側は `stage_probe` が測り直し、**1-Cの3区間が成立しなくなったことを
その場で名指し**しました。棚の高さ（崖つかまりが広がった分、1人で登れるように
なっていた）と最後の穴を直して、41チェックで通るところまで戻してあります。

### 特に大きかった設計の誤り：自動配置

「狙いが難しいなら狙わせるのをやめる。決定はどの道具かであって座標ではない」
という理屈で、タップした場所ではなくゲームが決めた場所に置いていました。

**この理屈は間違っていました。**しかも一番まずい間違い方で、
**プレイヤーが既に指した場所を黙って書き換えて**いました。
「壁ボタンを押すと全然違う所に壁ができる」は、ルールが少しズレているという
報告ではなく、**そのコントロールが信用できない**という報告です。丸ごと削除しました。

## 7. 今わかっている限界

### ① 実機での手触りと性能は測れません

この環境には端末がありません。**「気持ちいいか」「重くないか」は一度も
私の目を通らずに届いています。**浮き・点滅・位置ズレは今後テストが捕まえますが、
操作感の評価はあなたにしかできません。

### ② アートの権利 — App Store 公開の前に要対応

アートはいただいたモックアップからの切り出しで、その中に
**緑の土管・`?`ブロック・レンガ・キノコ型の敵・キノコ屋根の城**が含まれます。
任天堂の意匠として識別性が非常に高いものです。

- **TestFlight の Internal テスト**（非公開・招待した人だけ）→ 実務上の問題は小さい
- **App Store への公開提出** → リジェクトと権利者からの申し立ての対象になり得ます

画像は `Art.MANIFEST` を通しているので、**差し替えてもコードは一行も変わりません**。

### ③ 計測できていないもの

巡回中の敵の接地は、ピクセル計測が**7体中6体で取れていません**
（世界が動いていて画が止まらないため）。位置の一致は別のテストで見ていますが、
「絵として地面に接しているか」はこの6体ぶん未検証です。

### ④ 両方の端末が同じビルドである必要があります

通信フォーマットは現在 **version 4**。違うと黙って失敗はせず、
ガーディアンの画面に「バージョンが違います」と出ます。

### ⑤ ランナーのアニメーション

8ポーズ＋手続き的な動き（傾き・スクワッシュ・マフラー追従）です。
描き下ろしの多フレームアニメには届きません。
