# 1-S「THE OPEN SKY」設計

7 本目のステージ。既存 6 本（1-1 教習 / 1-C 協力パズル / 1-2 追跡 / 1-T 計測部屋 /
1-V 情報非対称 / 1-B ボス）に無いものを 1 つだけ足す：**《流れ》**。

そして、**使われていなかった道具 2 つを移動手段そのものにする。**

---

## 1. 埋める穴は 2 つあった

調査して分かったこと。

| 道具 | 実装 | テスト | **レベルデータでの要求** |
|---|---|---|---|
| **ワープ門**（スロット4・22ゲージ×2） | ある | ある | **一度も無い** |
| **射出**（足場タップ発射） | ある | ある | 1-C の**2 箇所だけ** |

射出は `launch_trigger.gd` のコメントで
**"the move the whole co-op idea is for"**（協力という発想そのもののための技）
と呼ばれている。それが 7 ステージ中 2 箇所。

ワープ門にいたっては、**どのステージの地形も一度もそれを必要としていない**。
能力ボタンの 4 つ目が、レベル設計から見ると存在しないのと同じだった。

1-S はその 2 つで出来ている。

---

## 2. 中身

### 一巡（これが全部）

```
   足場に立っている
        ↓
   ガーディアンが撃つ            （20ゲージ）
        ↓
   最大 665px 飛ぶ。ランナーは舵を取る
        ↓
   次の足場に降りる
     ・島               → ステージが置いたもの
     ・ガーディアンの足場 → 30ゲージ・5秒・同時2枚
        ↓
   その足場にも発射装置が付いている
```

四節（島が無い区間）では**着地点がガーディアンの板**で、その板は 5 秒で消える。
**飛んでいる間に次を置く**しかない。これが「流れ」の正体。

### 射出は「最大 665px」であって固定ではない

これがこのステージの中心にある事実で、**新しいコードは 1 行も要らなかった**。

| | |
|---|---|
| `AIR_MOMENTUM_DRAG = 60` | 射出の勢いに**逆らわなければ**、0.86 秒で 52px しか減衰しない |
| `RUNNER_AIR_TURN = 2736` | **押し戻すと** 0.285 秒で 780px/s が死ぬ |

つまりランナーは飛行中、**そのまま行くか、手前に落とすか**を選べる。
実測すると、逆に倒した射出は **-35px**（つまりほぼ真上に打ち上がって真下に落ちる）。

**二節はこの事実だけで出来ている。** 着地島を幅 170px・射出より手前に置くと、
惰性で行けば飛び越して落ちる。**舵を取れ、という要求が地形から出る。**

### 結晶は「線」で吊る

1 跳び = 足場 30 + 狙撃 20 = **50 ゲージ**。回復は毎秒 8 なので 6.25 秒ぶん。
これだけでは流れにならないので、**結晶（1個 34）を弧の上に並べる**。

最初は 1 弧につき 1 個だった。probe に飛ばせたら**0 個**拾った。理由は測って分かる：

- 結晶の当たり半径は **30px**
- 足場は幅 **150px**、`LaunchTrigger.loaded()` はその**どこに立っていても**発射を許す
- つまり**射出の開始位置が ±75px ぶれる**

1 個だと、不明な開始点から 30px の穴を通せという話になる。
なので **1 弧につき 3 個・70px 間隔の短い列**にした。
線に乗っていれば拾い、外れていれば拾えない。

> **良い線で飛べば次の射出が買える。外せば、待つ。**

弧の高さもモデルではなく実測：**180px 進んで 225px 上、380px 進んで 294px 上、頂点 296px。**
結晶はその 2 つの高さに吊ってある。

### ワープ門は「弧では届かない渡り」のためにある

射出の弧は固定（実測：平地 665、120px 上って 580、200px 上って 531、300px 上って 370）。
最終節の谷は **1,250px・60px 上り**。射出では届かない。

そして **`PLACE_MAX_RANGE` は 1,400px** なので、
**島の切れ端の上からなら向こう岸に門を置ける。**
切れ端に乗るには射出が要り、門を置くにはその切れ端に乗る必要がある——
**2 つの道具が直列につながる、ゲーム中で唯一の場所。**

代金は門 2 つで 44。足場＋狙撃と合わせて 94／100。だから見せ場になる。

## 3. このステージだけの新要素：**上昇気流**（1 つだけ）

**縦の帯。中にいるあいだ落下が上昇に変わる。**
ゲージを 1 も使わない唯一の高度（バネは地上、ワープは有料）。

実装は `Spring` と同じ形（`process_priority = 10` でランナーの後に走り、
`Clock.is_host` のときだけ `runner.velocity` に触る）。
**通信は 1 バイトも増えない**（位置は固定・物理はホストだけ・神側は絵だけ）。
`Protocol.VERSION` は **11 のまま**。

### 最初の調整は間違っていて、probe がそう言った

最初 `UPDRAFT_RISE = 300px/s` にした。落ち着いた数字に見えるが、**まったく効かない**：

> 780px/s で横切る runner が幅 210px の帯にいる時間は **0.27 秒**。
> 0.27 秒 × 300px/s = **81px**。

probe の出力がこれ：

```
...straight through a column:    331 up, 768 across     ← 素の射出 +35px
```

そこで「**止まって乗る**」設計に変えた。これも駄目だった、と計算で分かる：

> 横速度ゼロで帯の頂点まで昇った runner は、**その後落ちる高さの 0.3 倍しか
> 横に流れない**。つまり帯から出て何かの上に降りられない。

**結論：帯は「止まって乗るもの」ではなく「飛び抜けるもの」。**
`UPDRAFT_RISE = 650`、帯は幅 240px 以上。いま実測で：

| | 上昇 | 到達距離 |
|---|---|---|
| 素の射出 | 296px | 665px |
| **帯を抜けた射出** | **485px** | **971px** |

三節の登り（300px）は素の射出では絶対に届かず（300px 上る射出は 370px しか進まない）、
帯を抜ければ届く。

### 帯の置き場所には規則が 2 つある（どちらも probe が見つけた）

1. **島の真下に置かない。** 真下だと runner は島の裏に突き上げられて 200px 手前で止まる
   （`riding it lifts the runner back to the islands (217px up)` で落ちた）
2. **射出足場が置かれる線の上に置かない。** 島の右肩のすぐ先＝ガーディアンが板を置く場所。
   そこに帯があると、**runner は板に乗った瞬間に持ち上げられて、撃たれる前に流されていく**。
   トレースがこうだった：

```
f24 x=4854 y=237 floor=true      ← 板の上に立った
f36 x=4909 y=193 floor=false     ← 誰も撃っていないのに浮いている
```

四節にも帯を 1 本置いていたが、**消した**。最初の射出が帯を抜けて 1,209px 飛び、
向こう岸の **11px 手前**に落ちた——帯が四節を「三節の作り直し」に変えてしまっていた。
**一節に一つの考え**。三節は帯、四節は連鎖。

## 4. 構成（5 節＋助走）

| 節 | 教えること | 落ちたら |
|---|---|---|
| 0 | ここが端だ。遠くに灯台が見えている | 落ちない |
| 1 | **射出が道路**（580px と 530px、素の射出で届く） | **下の道**に乗る |
| 2 | **舵を取る**（幅 170px の島が射出より手前に） | 下の道 |
| 3 | **上昇気流**（300px の登り・600px 先） | 下の道 |
| 4 | **島が無い**（1,300px を板の連鎖で） | 下の道 |
| 5 | **ワープ門**（1,250px・下に何も無い） | **奈落** |

全長約 10,000px、チェックポイント 5。

### 下の道 ——「失敗は時間であって進行ではない」

1-V の救済棚と同じ思想（`implementation-plan.md` §5.6）。
islands の下、y=780 に**4 本の切れた道**。

**切れているのが要点。** 一本につながっていると、落ちることが
「静かな別ルート」になる。各切れ端の端に上昇気流が 1 本あり、
**その節の頭に戻す**（終わりに戻すと、落ちることが節を飛ばす手段になる——
最初の配置がまさにそれで、四節の 1,300px をタダで渡れた）。

**五節には下の道が無い。** そこだけが本当の死で、直前にチェックポイントがある。

### 敵

**飛行敵 4 体のみ**、飛行線の上。飛んでいる最中に対処はできないので、
**撃つなら射出の前**。砲台は置かない——空中で壁は使えないので、
ガーディアンの答えが無い敵になってしまう。

## 5. 何を測っているか

`test/sky_probe.gd`、**54 チェック**。`tools/verify.sh` に入れてある。

数字はすべて**その場で飛ばして実測**する（1-C の「射出の飛距離を重力の式で出したら
2 倍ずれていた」以来の作法）。

| 何を | なぜ |
|---|---|
| 射出の弧 4 種（平地／+120／+200／+300）と頂点 | 全ての谷幅の根拠 |
| **押し戻したときの到達距離** | 「弧は最大値」が本当か（二節の全部） |
| 弧の高さ（180px 地点・380px 地点） | 結晶をどこに吊るか |
| 全ての谷が「測った弧」の内側 | 到達性監査（1-C と同じ） |
| **見せ場が 3 つ**（帯・連鎖・門）であること | 各節が別の問題であること |
| 帯を抜けた射出の上昇と到達距離 | 新要素が効いているか |
| **帯がクライアントでは効かない** | ホスト権威。二台で位置がずれる形の穴 |
| 門を抜けて**速度が保存**されること | 1 フレーム ぶんの重力まで許容して比較 |
| 下の道が 4 本に切れていること／五節の下に無いこと | 失敗の代価の設計どおりか |
| **一節を実際に飛んで結晶を数える** | 経済が回るか（実測 3 個・102 ゲージ） |
| **三節を実際に飛んで向こう岸に降りる** | 帯の渡りが成立するか |
| **四節を実際に板 2 枚で渡る** | 連鎖が成立するか |
| **五節を実際に門で渡る** | ワープ門が初めて仕事をするか |
| 射出中にランナーが画面から出ないこと | 780px/s はゲーム中最速。カメラは横だけ |
| 登録簿に必要な絵のキーが全部あること | 素材監査 |

### 負のコントロール（4 本、実施済み）

| 壊したもの | 結果 |
|---|---|
| 上昇気流の揚力を消す | **8 チェックが落ちた** |
| 救済の帯を射出足場の線の上に戻す | **4 チェックが落ちた**（上で書いた実バグの再現） |
| ワープの移送を止める | **2 チェックが落ちた** |
| 最終節の谷を射出の届く幅に狭める | **2 チェックが落ちた** |

### 設計を作り直させた測定

**probe が地形を 3 回書き直させた。**

1. 三節の着地島が、runner が実際に降りてくる場所の **400px 手前**にあった
2. 救済の帯 3 本が、射出足場の置かれる場所に重なっていた
3. 四節の帯が、四節そのものを消していた

どれも「動くかどうか」ではなく「**その節が訊いている問いが成立しているか**」の話で、
目で見ても分からない種類のものだった。

## 6. 絵

素材は `docs/art-prompts-sky.md` の生成待ち（9 枚）。
**1 枚も無くても最後まで遊べる。**

ただし 1-B で学んだとおり、**ベクターのまま既定の配色だと「素材待ち」ではなく
「間違い」になる**——雲海の上のステージにキノコの城が建っていた。
なので 1-S 専用のフォールバックを入れた：

| | |
|---|---|
| 空 | 夜明けの勾配（上が濃紺、雲の線で金） |
| 中景 | **丘と城とブッシュを描かない**。代わりに**雲の海**を 2 層 |
| 島 | 淡い石＋苔の縁（`terrain.gd` の `_palette()`） |
| 島の底 | `keel` 装飾——下に細くなる岩と垂れた鎖。**「下に何も無い」を絵で言う要** |
| 上昇気流 | 縁が明るい帯＋**上向きのシェブロン**＋昇る粒 |

最後のものも実画面を撮って直した。最初の帯は
**1280x720 でほとんど見えなかった**（このステージ唯一の新要素なのに）。
1-B の突進予告と同じ直し方で、帯に**矢印**を入れたら読めるようになった。

`Art.PENDING` に 9 キーを登録してある。**例外そのものも監査している**ので、
ファイルが届いたのにリストに残っていればテストが落ちる。
