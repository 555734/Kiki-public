# 2人通信の設計（EOS / Listen Server 方式）

企画書 8章はオンライン同期を MVP 必須に挙げ、9章はそのリスクを
**「オンライン遅延で足場生成がズレて落下」**と名指ししている。この文書はその一点を
中心に据えて全体を組み立てる。

**最重要条件：開発者が常時稼働させるサーバーを 1 台も持たない。**
プレイヤーが 2 人から 2 万人になっても、こちらの月額は **0 円のまま**にする。

---

## 0. 結論（先に3行）

1. **ホストはランナー側の端末**。専用サーバーもリレーサーバーも自前では持たない。
2. **EOS の Connect / Lobby / P2P（NAT Traversal + Relay）だけ**を使う。
   この 4 つは Epic が無料で提供していて、**リレー帯域も課金されない**。
   通常なら自前で立てて課金が発生する TURN が、これで丸ごと消える。
3. コア体験（飛んでから足場で救出）は、**ホスト側の巻き戻し**で守る。
   「ガーディアンの画面では間に合っていた」なら、**間に合ったことにする**。
   ただし**助ける方向にしか転ばない**——不利になる巻き戻しは採用しない。

---

## 1. なぜランナーがホストなのか

普通のマルチプレイ設計は全員を平等に扱う。このゲームではそれが間違いになる。

| | 必要な応答性 | 理由 |
|---|---|---|
| **ランナー** | **1フレームも遅らせられない** | 反射でジャンプする。入力遅延＝操作不能 |
| **ガーディアン** | **150ms 遅れても成立する** | 企画書6章の通り「数秒先」を読んで動く。反射ではなく計画 |

だから**シミュレーションはランナーの端末で回す**。「先に部屋を立てた方がホスト」ではなく
**役割でホストを決める**。これが設計上いちばん重要な判断で、これ一つで：

- ランナーの入力遅延が **構造的にゼロ**になる（予測もロールバックも要らない）
- そして——**「画面では足場に乗ったのにホスト側では落下していた」という現象が、
  ランナー側では原理的に起こらなくなる。**
  ランナーの画面がホストの画面であり、それが正解だから。

残るのは裏返しの問題だけになる：
**「ガーディアンの画面では間に合わせたのに、ホストではもう落ちていた」。**
これは 8 章で詳しく潰す。片方向の問題に還元できたこと自体が、この配置の成果。

```
  ランナー端末（ホスト・権威・Listen Server）      ガーディアン端末（クライアント）
  ┌──────────────────────────┐                ┌──────────────────────────┐
  │ 入力 → 物理 → 描画（遅延0）  │  30Hz スナップ  │ 100ms 過去を補間して描画    │
  │ 権威ある世界状態             │ ─────────────> │ 自分の UI は全部ローカル予測 │
  │ 巻き戻しバッファ 400ms       │                │                          │
  │ コマンドを検証・遡って適用     │ <───────────── │ 照準（30Hz）・能力（イベント）│
  └──────────────────────────┘                └──────────────────────────┘
                    EOS P2P（NAT越え失敗時は EOS Relay・無料）
```

### 役割交換したら

`Tab` の役割交換はオンラインでは**ホスト移譲**を意味する。移譲中に走らせるのは危険なので、
**交換はチェックポイント到達時とステージ境界でのみ許可**する。そのタイミングでは
世界がどのみちリセットされるので、移譲は「小さな永続状態（チェックポイント番号・
ゲージ・残機）を渡して、新ホストがそこから作り直す」だけで済む。
走行中の交換要求はキューに積んで、次のチェックポイントで実行する。

### ホスト側の回線が悪かったら

それでもランナーがホストのまま。**遅延の非対称性は帯域より重い**からで、
ホストを変えるとランナーの操作性が直接壊れる。回線品質は EOS Relay が吸収する。

## 2. EOS のどれを使い、どれを使わないか

| EOS 機能 | 使う | 用途／理由 |
|---|---|---|
| **Connect**（Product User ID） | **使う** | 全 API の前提。Device ID で**匿名ログイン可**、Epic アカウント不要 |
| **Lobby** | **使う** | 2人部屋・招待コード・メンバー属性・**オーナー移譲が組み込み**。今回のマッチングはこれで足りる |
| **P2P (NAT P2P)** | **使う** | 実通信。`SendPacket`/`ReceivePacket`、チャネル 0-255、1170B/パケット、信頼性3段階 |
| **NAT Traversal + Relay** | **使う** | P2P に内包。**穴あけ失敗時に Epic のリレーへ自動フォールバック、帯域は無料** |
| **Auth**（Epic アカウント） | 使わない | モバイルで Epic ログインを強制したくない。Connect の Device ID / プラットフォーム連携で足りる |
| **Sessions** | **使わない** | 専用サーバー・サーバーブラウザ・マッチメイキング向け。2人招待制には Lobby の方が素直で、Sessions を足すと概念が二重になる |
| **Matchmaking (P2P Sessions)** | 使わない | 野良マッチをやらないため。将来やるなら Lobby Search の属性検索で足りる |
| **Player Data Storage** | 使わない（将来） | クラウドセーブ用。現状セーブは端末ローカルで足りる |
| **Anti-Cheat (EAC)** | **使えない** | **モバイル未対応**、かつサーバー側 EAC は専用サーバー前提。10章で正直に扱う |
| **Voice (RTC)** | 使わない（将来） | Lobby に統合されていて無料。同室プレイ前提なので今は不要 |

### Connect のログイン方式

1. **Device ID**（`EOS_Connect_CreateDeviceId` → `EOS_ECT_DEVICEID_ACCESS_TOKEN`）
   — 匿名・摩擦ゼロ。初回起動でそのまま遊べる。**これを既定にする。**
2. 端末を乗り換えたい人向けに、後から Google Play / Apple Sign-In を紐付ける導線を用意。

Device ID は端末を消すと失われるので、「進捗は端末に紐づく」ことを設定画面で明記する。

### 招待の流れ（サーバー費 0 円で成立させる）

```
P1（ランナー）: Lobby 作成（max 2, presence enabled）
                → Lobby ID から 6桁コードを生成して画面に表示
P2（ガーディアン）: コード入力 → Lobby Search（属性 join_code に一致）→ Join
両者:            Lobby メンバー属性から相手の PUID を取得
                → EOS_P2P_AcceptConnection → 以後 SendPacket/ReceivePacket
```

**この経路のどこにも自前サーバーが無い。** 部屋の発見も、NAT 越えも、失敗時のリレーも、
全部 EOS が持っている。前の設計（Cloudflare Workers のシグナリング＋自前 TURN）で
唯一お金がかかりうる TURN が、ここで消える。

## 3. 権威（authority）の分割

**原則：世界に影響するものは全部ホスト。クライアントは「意図」しか送らない。**

### ホスト（ランナー端末）が権威を持つもの

| 対象 | 内容 |
|---|---|
| 時刻 | **tick（60Hz の整数）**。全同期の基準。世界の唯一の時計 |
| ランナー | 位置・速度・状態・向き・HP・無敵時間・コヨーテ/ジャンプ残時間 |
| 敵 | 位置・AI 状態・HP・生死・弾の発射 |
| ホログラム | 足場/壁の **生成位置・生成 tick・消滅 tick**・枚数上限の適用 |
| ギミック | スイッチ ON/OFF と残時間、扉の開閉、崩落床の起動/崩落/復活 |
| 共通ゲージ | **値そのもの**。消費の可否判定 |
| 進行 | チェックポイント番号、死亡、リスポーン、ステージクリア |
| 判定 | 踏みつけ、被弾、狙撃の命中、足場に乗ったかどうか |

### ガーディアン（クライアント）が権威を持つもの

**世界状態については何も持たない。** 持つのは自分の意図と自分の UI だけ：

- 照準座標（送るが、当たり判定はホストが再計算する）
- 「いま tick T の描画を見て、座標 P に足場を置きたい」という**要求**
- スロット選択・スコープ倍率（純粋に自分の表示）
- 自分の画面の予測表示（ゴースト足場・ゲージの先読み減算・発砲エフェクト）

この分け方だと、ガーディアンの**操作感は 100% ローカル**で、遅延するのは
「世界に効いたかどうか」だけになる。UI が固まる瞬間が存在しない。

## 4. 通信量の3分類

ユーザー指定の分類。**ここが帯域設計の本体。**

### (A) 毎フレーム（正確には 30Hz）送るもの — 連続的に変化し、予測しきれないもの

| 向き | 内容 | サイズ |
|---|---|---|
| ホスト→GD | tick | 2 B |
| ホスト→GD | ランナー位置（x: 1/2px, y: 1/8px） | 4 B |
| ホスト→GD | ランナー速度（1/8 px/s ×2）※補間に使う | 4 B |
| ホスト→GD | 状態 enum + 向き + 接地 + 無敵（ビットパック） | 1 B |
| ホスト→GD | 共通ゲージ（0-100） | 1 B |
| ホスト→GD | ランナー HP + フラグ | 1 B |
| ホスト→GD | **「既定値からズレた敵」だけ**（後述） | 通常 0 B |
| **計** | | **13 B ＋ ヘッダ（実測）** |

**この 13 B は手計算ではなく `Snapshot.quiet_size()` の実測値**で、
`test_bandwidth_budget` が予算を超えたら落ちる。

**量子化の精度は軸ごとに変えている。** 16bit では 18,300px のステージを 1/8px で
表現できないため：

| 軸 | 精度 | 範囲 | 誤差 |
|---|---|---|---|
| x | 1/2 px | -2048 〜 30719 | 0.25px（1 tick の移動 6px に対して見えない） |
| y | **1/8 px** | -1024 〜 7167 | 0.06px |

**精度を y に寄せている**のは、足場に乗ったかどうかを決めるのが y だから。
範囲外は**クランプする（絶対にラップさせない）**——ラップするとステージの反対側に
瞬間移動して、テレポートチートのように見えるバグになる。
| GD→ホスト | 照準座標（×2）＋直前2サンプル（冗長） | 12 B |
| GD→ホスト | 最後に受け取った tick（ack） | 2 B |

30Hz × 13B ≒ **0.4 KB/s**。EOS/UDP のヘッダを乗せても**両方向合計 3 KB/s に届かない**。
10分のセッションで 2 MB 弱。モバイル回線でも問題にならない。

### (B) イベント時だけ送るもの — 離散的で、起きた瞬間が意味を持つもの

すべて **ReliableOrdered**。頻度は毎秒数回以下。

| 向き | イベント |
|---|---|
| GD→ホスト | `PLACE{kind, 座標, view_tick, seq}` 足場/壁の設置要求 |
| GD→ホスト | `FIRE{照準座標, view_tick, seq}` 狙撃 |
| GD→ホスト | `SLOT{n}` スロット選択（表示同期のためだけ） |
| ホスト→GD | `HOLO_SPAWN{id, client_seq, kind, 座標, birth_tick, death_tick}` |
| ホスト→GD | `HOLO_KILL{id, 理由}`（上限超過で最古が消えた等） |
| ホスト→GD | `REJECT{client_seq, 理由}` 設置/狙撃の却下 |
| ホスト→GD | `HIT{enemy_id, tick}` / `ENEMY_DIE{enemy_id, tick, 理由}` |
| ホスト→GD | `SWITCH{id, on, expire_tick}` / `GATE{id, open}` |
| ホスト→GD | `CRUMBLE{id, armed_tick}` / `CRUMBLE_GONE{id, respawn_tick}` |
| ホスト→GD | `RUNNER_HURT{hp, tick}` / `RUNNER_DIE{tick, 原因}` / `RESPAWN{cp, tick}` |
| ホスト→GD | `CHECKPOINT{index}` / `STAGE_CLEAR{...}` |
| 双方向 | `PING{t}` / `PONG{t, host_tick}` 1秒ごと（RTT 推定） |

**消滅時刻をイベントで送らない**のがポイント。`HOLO_SPAWN` に `death_tick` を含めるので、
消滅は両者がローカルで同じ tick に実行する。**消えるためのパケットは 0 通。**

### (C) 送らないもの — ローカルで完全に再現できるもの

**これを増やすのが帯域削減の本体。** tick という共通の時計があれば、時間の関数で
書けるものは全部ここに落ちる。

| 対象 | なぜ送らなくていいか |
|---|---|
| ステージ地形・装飾・背景 | 両者が `Level01Data` を持っている。定数 |
| **移動床の位置** | `tick` の純関数にする（下の 4.1）。**送信 0 B** |
| **レーザーの ON/OFF 位相** | 同じく `tick` の純関数。**送信 0 B** |
| **無傷の敵の巡回位置** | 両者が**同じ AI をローカルで回す**。ただし純関数ではないので低頻度の補正を入れる（4.3） |
| 砲台の発射周期 | `tick` の純関数にできる（未着手）。ただし**弾が当たる**ので発射だけはイベント |
| 弾の飛翔位置 | 発射 tick・原点・速度から両者が同じ軌道を出せる |
| ホログラムの残り時間表示 | `death_tick - 現在 tick` |
| ゲージの自然回復 | 毎秒 +8 の決定的な関数。**消費イベントの時だけ**同期すればいい |
| ランナーのアニメ・脚の回転・マフラー | 同期された状態から導出 |
| 土煙・着地パフ・被弾火花・ヒットストップ | 演出。イベントから両者が生成 |
| カメラ位置・シェイク・視差 | 完全にローカル |
| 照準リング・スコープ倍率・HUD | ガーディアンのローカル |
| **コインを取ったこと** | 両端末が自分の持っているランナー位置で同じ判定を回す。見た目は両方で消え、ゲージはホストのものがスナップショットで届く |
| **バネが跳ねたこと** | 跳躍そのものはホストがランナーの速度に書く。パッドの潰れる演出は、**跳ね上がっている速度そのもの**から両端末が導出する |
| **ワープの往復** | 5.4b。1tick で 300px 以上動いたスナップショットが、そのままワープの通知になっている |

### 4.1 「時間の関数にする」ための実装変更（実施済み）

`MovingPlatform` と `Laser` は `_physics_process(delta)` で自前に時間を累積していた。
これだと浮動小数の累積誤差と、フレーム落ちで**両端末がじわじわズレる**。

権威 tick から引くように変えた：

```gdscript
# 変更前： _time += delta                     ← 端末ごとに違う値になる
# 変更後： var t := Clock.seconds(phase_offset) ← tick の純関数。必ず一致する
```

`Clock` はホストが tick を進め、クライアントはスナップショットの tick に追従する
オートロード。これで**移動床とレーザーの同期パケットが完全に不要**になった。
`test_determinism` が、同じ tick から独立に 2 回計算して結果が一致することを見張る。

### 4.3 敵は「純関数」ではない——正直に扱う

移動床とレーザーは `tick` を入れれば答えが出る**閉じた式**にできた。
**歩行敵はできない。** 企画書通り「崖のふちで引き返す」ので、地形との衝突判定が要り、
`move_and_slide()` を通る。つまり**閉じた式ではなく、同じ入力から同じ手順を踏む
ロックステップ**にしかならない。

そしてロックステップには落とし穴がある：**異なる端末・異なるビルドで浮動小数と
物理エンジンがビット単位で一致する保証は無い。** ARM と ARM でも、Godot の
バージョン差でも、じわじわズレうる。「決定的だから送らなくていい」で済ませると、
数分後に敵が別の場所に居る。

なので敵はこう扱う：

| | |
|---|---|
| クライアント | 同じ AI をローカルで回す（＝**予測**であって真実ではない） |
| ホスト | **1 スナップショットにつき 1 体ずつ、順繰りに**位置を載せて補正する |
| 逸脱時 | 撃たれた・踏まれた・ノックバック中の敵は毎回載せる |
| 死亡 | `ENEMY_DIE` を Reliable で 1 回。以後は両者とも「居ない」 |

順繰り補正のコストは **6 B/tick = 180 B/s**。敵 20 体なら 1 体あたり 0.66 秒に 1 回
補正が入るので、ドリフトは目に見える前に潰れる。
`Snapshot.dirty_enemies` がこの枠をそのまま使う（形式は同じで、載る理由が違うだけ）。

**「決定的だから 0 B」と言い切れるのは移動床とレーザーだけ**で、そこは
`test_determinism` が実際に検算している。敵まで同じ扱いにしないのが、
この節の要点。

### 4.2 敵は「ズレた分だけ」送る

敵 20 体を毎フレーム送ると 20×6B = 120B/tick になり、他の全部より重くなる。
だが**無傷の巡回敵は tick の純関数**なので、送る必要があるのは
「既定の巡回から外れた敵」だけ：撃たれた・踏まれた・死んだ・ノックバック中。

スナップショットには `dirty_enemies` の可変長リストを入れる（通常は空、長さ 1 B）。
死んだ敵は `ENEMY_DIE` イベントで一度だけ送り、以後は両者とも「居ない」で一致する。

**結果：通常戦闘中の敵の帯域は実質ゼロ。**

## 5. 各対象の同期方式

### 5.1 ランナーの位置・速度・ジャンプ

- **送るのは状態であって入力ではない。** ランナーの入力は端末から一切出ない
  （ホストなので出す必要がない）。
- 30Hz で 位置・速度・状態 enum・接地フラグ。
- ガーディアン側は**位置と速度の両方を使う 3 次エルミート補間**。
  線形補間だとジャンプの放物線が折れ線になり、頂点が潰れる。速度が既に入っているので、
  エルミートは追加コスト 0 B でカーブが正しくなる。
- **ジャンプは「イベント」ではなく状態として伝わる。** 別途 `JUMP` パケットを送らない。
  速度 y が負に転じたスナップショットが届けばそれがジャンプで、補間が勝手に弧を描く。
  可変ジャンプの高さも速度に現れるので、**追加情報ゼロで正しく見える**。
- 演出（土煙・スクワッシュ）は状態遷移から**ガーディアン側が自前で**生成する。

### 5.2 敵の位置 / AI / HP

| | 方式 |
|---|---|
| 位置 | 無傷なら **tick の純関数**（送らない）。逸脱中のみスナップショットに載せる |
| AI | ホストのみが実行。クライアントは**同じ決定的 AI をローカルで回す**（無傷の間は必ず一致） |
| HP | ホスト権威。**変化した瞬間だけ** `HIT` イベント |
| 死亡 | `ENEMY_DIE{id, tick}`。以後クライアントもローカル AI を止める |
| 弾 | `SHOOT{turret_id, tick, origin, velocity}` の 1 イベント。以後の軌道は両者が同じ式で描く |
| ノックバック | 逸脱状態なので、収まるまでスナップショットに載る |

### 5.3 ガーディアンの照準・狙撃

- **照準**：30Hz でワールド座標を送る。**当たり判定には使わない**——ホストは
  `FIRE` に添えられた座標で判定する。照準の連続送信は、ランナー側に
  「相棒がどこを狙っているか」を見せるためだけの演出用。落ちても害がない
  ので Unreliable。1パケットに直近3サンプル入れて欠損に耐える。
- **狙撃**：`FIRE{aim, view_tick, seq}` を Reliable で。ホストは
  **敵の位置を `view_tick` まで巻き戻して**当たり判定する（FPS のヒット判定と同じ
  ラグ補償）。巻き戻しは最大 250ms。
  - 巡回敵は tick の純関数なので、**過去位置を保存せず数式で逆算できる**。
    逸脱中の敵だけリングバッファを見る。
  - 巻き戻すのは**敵だけ**。ランナーは絶対に巻き戻さない（味方に当たらないので不要）。
- ガーディアン側は発砲時に**即座に**マズルフラッシュと着弾スパークを出す（予測）。
  外れていた場合は敵が死なないだけ。**「却下」ポップアップは出さない**——
  外したのか遅延なのかを演出で区別させても、プレイヤーにできることは無い。

### 5.4 足場 / 壁：生成位置・生成時刻・消滅時刻

ここが企画書 9章のリスクそのものなので、章を分けて 8 章で詳述する。同期の形だけ先に：

| | 方式 |
|---|---|
| **生成位置** | ガーディアンが**ワールド座標**で要求。「ランナーの下」のような相対指定は禁止（遅延で意味が変わる） |
| **生成時刻** | ホストが決める。ただし**ガーディアンの `view_tick` まで遡って**設定しうる（＝バックデート） |
| **消滅時刻** | ホストが `birth_tick + 寿命` を計算して `HOLO_SPAWN` に同梱。**以後同期不要** |
| **枚数上限** | ホスト権威。3枚目で最古が消えるのもホストが決め、`HOLO_KILL` で通知 |
| 表示 | ガーディアンは要求と同時にゴーストを出す。確定パケットで実体に差し替える |

### 5.4b ワープゲート（能力4）

構造体としては足場・壁と同じ扱いにした。`HOLO_SPAWN` の `kind` バイトは
もともと 0/1 の 2 値しか使っておらず、そこに 2（WARP）を足しただけなので
**新しいパケットは 1 種類も増えていない**。

| | 方式 |
|---|---|
| **生成位置** | 足場と同じ。ワールド座標で要求、ホストが可否を判定 |
| **生成時刻** | **バックデートしない。** 巻き戻しは「落ちているランナーが足場に乗れたか」を判定する仕組みで、ゲートは乗るものではない。過去に遡らせると、ランナーがもう通り過ぎた位置へ飛ばすことになる |
| **対消滅** | 3つ目を置くと古い1組が消える。この規則は**パケットで送らない**——両端末が `Guardian.spawn_hologram` で同じ規則を同じ順序のゲート列に適用するので、勝手に一致する（4章 (C) と同じ理屈） |
| **転送そのもの** | **ホストのみ。** ランナーの位置はホストのもので、クライアントが自分のパペットを動かしてもスナップショットで上書きされるだけ |
| **クライアント側の見え方** | 1tick で 300px 以上動いたスナップショットは補間せず**スナップさせる**。走行の最高速でも 33ms で 15px 程度なので誤判定しない。ワープを知らせるパケットは無い |

3つ目の規則を「最古を1つ消す」（足場と同じ）にしなかったのは、
**昨日の出口と今日の入口が組になる**からで、それは誰にも狙えない。

### 5.5 スイッチ・扉・崩落床

すべて**イベント + 期限**の形にして、途中の毎フレーム同期を無くす。

- `SWITCH{id, on, expire_tick}` — 6秒後に閉じるのは両者がローカルで実行
- `GATE{id, open}` — スイッチから導出できるが、**ズレたら詰む**ので明示的に送る（安いので）
- `CRUMBLE{id, armed_tick}` — 起動した瞬間だけ。崩落は `armed_tick + CRUMBLE_DELAY` で両者一致
- `CRUMBLE_GONE{id, respawn_tick}` — 復活時刻を含めるので復活パケットは不要

崩落床は**ランナーが踏んだ瞬間**にホストが起動を決める。ガーディアンの画面では
100ms 遅れて起動するが、ガーディアンにできることは「別の足場を出す」ことだけなので
実害がない。**逆にホストが遅れる経路が存在しない**のが効いている。

### 5.6 共通ゲージ

- **値の権威はホスト。** これは譲れない：ゲージは企画書 9章の
  「神側が強すぎるとランナーが駒になる」を潰す唯一の制約なので、
  クライアントに持たせると制約そのものが消える。
- ただしガーディアンは**先読みで即座に減算**して表示する。回復は毎秒 +8 の決定的な
  関数なので、予測はほぼ常に当たる。
- スナップショットの権威値との差が 1 を超えたら、**150ms かけて寄せる**（スナップさせない）。
  ゲージバーが飛ぶと「取られた」ように見えるため。
- **足りない時の拒否はクライアント側でも同じ関数で判定して、送らずに弾く。**
  `GuardianAbility.check()` を両者が持っているので、
  「ゲージ不足」「置ける場所がない」の大半は往復せずに解決する。
  ホストとクライアントで判断が割れた時だけ `REJECT` が飛ぶ。

## 6. Client Prediction / Interpolation / Reconciliation

このゲームは**クライアントがキャラクターを操作しない**ので、
教科書的な「入力予測＋サーバー照合」は要らない。必要なのは形を変えた3つ。

### 6.1 Client Prediction（ガーディアン側）

予測するのは**自分の操作の結果のうち、自分の画面だけで完結する部分**：

| 予測するもの | 確定までの見せ方 |
|---|---|
| ゴースト足場 | 要求と同時に半透明で出し、**RTT と同じくらいの「実体化アニメ」**を再生する。確定パケットはそのアニメの最中に届くので、待たされている感じにならない |
| ゲージの減算 | 即座に引く。権威値に緩やかに寄せる |
| 発砲エフェクト | 即座。命中は待つ |
| スロット選択・倍率 | 完全ローカル。往復しない |

**ランナー側には予測が一切要らない。** ホストなので。ここが構造上いちばん得をしている点。

### 6.2 Interpolation（ガーディアン側）

- 描画 tick = `最後に受けた tick − interp_ticks`。
- `interp_ticks` は**ジッタに応じて 2〜6 tick（66〜200ms）で自動調整**。
  到着間隔の分散を指数移動平均で見て、詰まりすぎたら伸ばす。
- 補間は**位置＋速度のエルミート**。
- 補間バッファが尽きたら（パケットが来ない）、**最大 3 tick だけ速度で外挿**して、
  それ以上は最後の状態で固める。外挿しすぎるとランナーが壁にめり込んで見える。

### 6.3 Reconciliation

ガーディアン側の「予測したもの」と「権威が返したもの」の突き合わせ。
`client_seq` で対応付ける。

| ケース | 処理 |
|---|---|
| 確定が来た（一致） | ゴースト → 実体に差し替え。**位置はクライアントが送った値そのまま**なので動かない |
| 確定が来た（`birth_tick` が過去） | 実体化アニメを**その分だけ進めた状態**から始める。時間が飛んだように見せない |
| `REJECT` が来た | ゴーストを**消すのではなく散らす**（ポップより気づきやすく、かつ不快でない）。ゲージを戻す |
| 1秒待っても何も来ない | ゴーストを散らしてゲージを戻す。パケットロスの保険 |
| ゲージが権威とズレた | 150ms で寄せる |
| 敵の位置が権威とズレた（逸脱） | 補間の目標を差し替える。瞬間移動はさせない |

**ランナー側の Reconciliation は 1 種類だけ存在する**——8章の巻き戻しを採用した時の
視覚補正。物理ボディは即座に正しい位置へ、**見た目のノードだけ 100ms かけて追いつく**。

## 7. パケットロスへの対応

### チャネル設計（EOS P2P は 0-255 のチャネルと 3 段階の信頼性を持つ）

| ch | 内容 | 信頼性 | ロス時の扱い |
|---|---|---|---|
| 0 | スナップショット | Unreliable Unordered | **捨てる。** 次が 33ms 後に来る |
| 1 | 世界イベント（ホスト→GD） | **Reliable Ordered** | EOS が再送。順序も保証 |
| 2 | 能力コマンド（GD→ホスト） | **Reliable Ordered** | 同上。設置と狙撃は落としてはいけない |
| 3 | 照準ストリーム（GD→ホスト） | Unreliable Unordered | 捨てる。**1パケットに直近3サンプル**入れてあるので実質ロスしない |
| 4 | ping / 握手 / 再同期要求 | Reliable Ordered | 1秒に1回 |

### 方針

- **スナップショットは差分圧縮しない。** 13 B しかないので、差分にする利得より
  「差分の基準パケットが落ちると連鎖する」リスクの方が大きい。
  **毎回フルで送る**ので、どれだけ落ちても次の 1 通で完全に復帰する。
  これは 2 人・小状態だから取れる選択で、そう書いておく。
- **ホストは絶対にクライアントを待たない。** 照準が来ていなくてもシミュレーションは進む。
  待つ設計にすると、ガーディアンの回線がランナーの操作性を壊す。
- **重複と順序逆転**：イベントは `seq` を持ち、ホストは処理済み `seq` を記録して
  冪等に弾く（EOS の Reliable Ordered があっても、再接続をまたぐと必要になる）。
- **バースト欠損（モバイルのハンドオーバー等）**：0.5 秒スナップショットが途切れたら
  ガーディアンは補間を止めて「同期中」表示。2 秒で `RESYNC` を要求し、
  ホストがフル状態（後述 200〜400 B）を 1 通返して即座に復帰する。
- **`view_tick` の妥当性**：クライアント申告の `view_tick` は
  `now - min(MAX_REWIND, 実測RTT/2 + interp + 余裕)` で下限クランプする。
  ロスで古い tick を申告してきても、巻き戻しが青天井にならない。

## 8. ★核心：足場救出のラグ補償

企画書 10章の「飛んでから足場を置いて救出する」——この瞬間だけは、
**遅延で失敗したら体験そのものが壊れる**。名指しで設計する。

### 8.1 どの失敗が残っているのか

ランナーがホストなので、失敗の形は**1つに絞られている**：

> ガーディアンの画面（ホストより Δ=100〜200ms 過去）ではランナーの真下に置けたのに、
> パケットが届いた時にはホストのランナーはもう Δ 分落下していて、足場が頭上に出る。

### 8.2 対策1：ガーディアンには「未来のランナー」を見せる

いちばん効くのは、そもそも過去を狙わせないこと。

ガーディアンの画面には、補間された（＝過去の）ランナーに加えて、
**Δ 後の予測位置に薄いリードゴースト**を描く。設置プレビューはそのゴーストに吸着する。
つまり**ガーディアンは未来を狙う**。これだけで大半のケースが補償なしで成立する。

Δ はこちらが実測している値なので、プレイヤーは「遅延を意識せず、見えているものを狙う」
だけでよい。**遅延の存在をUIに翻訳して隠す**、という考え方。

### 8.3 対策2：ホスト側の巻き戻し（バックデート設置）

対策1で拾えなかった分——ガーディアンが過去のランナーを狙った場合——を拾う。

**実装状況**：下の擬似コードのうち、1（安いふるい）・3（助ける方にしか転ばない判定）と、
8.4 の掃引捕捉は**入っていてテストがある**。2 の完全な再シミュレーションは**まだ**——
掃引捕捉が核心のケース（落下中に足場が遅れて出る）をそのまま拾えるので、
先に安い方だけを入れた。**足場が壁のようにランナーを止める**ケースなど、
掃引だけでは足りない状況が出たら 2 を足す。

`PLACE{P, view_tick, seq}` を受けたホストの手順：

```
rewind = clamp(now - view_tick, 0, MAX_REWIND)          # MAX_REWIND = 15 tick = 250ms
rewind = min(rewind, 実測RTT/2 + interp + 余裕)          # 申告の水増しを潰す
if rewind == 0: 普通に生成して終わり

# ── 1. 安いふるい ──────────────────────────
# 過去 rewind tick のランナーの掃引経路と、足場の矩形が交差しないなら、
# この足場はランナーに一切関係しない。巻き戻す理由がない。
if not 掃引経路.intersects(足場矩形 を上に少し広げたもの): 普通に生成して終わり

# ── 2. 投機的な再シミュレーション ────────────
S_now = 現在の権威状態を退避
ランナーを ring[now - rewind] の状態に戻す
足場を birth_tick = now - rewind で挿入
for t in (now-rewind .. now]:
    記録済みの入力で 1 tick 進める          # ランナーの入力は全部ホスト内にある
S_alt = 結果

# ── 3. 「助ける方にしか転ばない」判定 ──────────
if S_alt.生存 and S_alt.y <= S_now.y and not S_alt.針の中 and not S_alt.壁の中:
    S_alt を採用     # 救出は「間に合っていたこと」になる
else:
    S_now に戻し、足場は now で生成      # 助けにはならなかったが、遅れて出る
```

**この設計の要点は 3 段目の非対称性：**

> **巻き戻しはランナーを助けることしかできない。**
> 再シミュレーションの結果が「死んだ」「さっきより低い位置にいる」「針の中」なら、
> **その結果は捨てる。**

ガーディアンの回線がどれだけ悪くても、**ランナーが理不尽に殺されることは原理的に無い**。
最悪でも「助けが遅れた」で止まる。ホスト＝ランナーである以上、
ランナーを勝手に巻き戻して不利にするのは絶対にやってはいけない。

再シミュレートするのは `CharacterBody2D` 1体 × 最大 15 tick。モバイルでも誤差の範囲。

### 8.4 対策3：着地の寛容さ（ネットコードではなくゲームデザイン側）

上2つで足りなかった数十 ms を、**判定の甘さ**で吸収する。
これは実は最も体感に効く層で、オフラインでも同じだけ効く。

| 仕掛け | 内容 |
|---|---|
| **着地マグネット** | 巻き戻し判定では、足場の上面を線ではなく **±24px の帯**として扱う。**これが実際に効いている**：終端速度でランナーは 1 tick に 18px 落ちるので、線で判定すると「1フレーム分未満の差」で救出を取りこぼす |
| **掃引捕捉** | 巻き戻し中、ランナーの経路が上面の帯を**下向きに横切っていた**なら、その交点に着地させて y 速度を 0 にする。再シミュレーションより安く、核心のケースをそのまま拾う |
| **落下速度の上限** | `RUNNER_TERMINAL_VELOCITY = 1100`。1 tick あたり最大 18px しか進まないので、15 tick 巻き戻しても取りこぼしが 1 枚分を超えない |
| **足場を厚く** | 見た目より当たり判定を数 px 厚くする。すり抜けの物理的余地を減らす |

### 8.5 それでも間に合わなかった時

`REJECT` は出さない。**足場は必ず出る**（遅れて）。ランナーは落ちる。
そこで初めて「間に合わなかった」という**ゲームの失敗**として提示する。
ネットワークの都合をプレイヤーに見せない。

### 8.6 逆向きの保証

念のため明記する。ユーザーが挙げた
**「画面では足場に乗ったのにホスト側では落下していた」**——
これは**ランナーの画面がホストである以上、発生しない**。
ランナーが乗ったと見たなら、それが権威の事実。
この問題を「起きうる側」から「起きえない側」へ移すことが、
ホスト選定でいちばん買いたかったものだった。

## 9. 切断・再接続・途中参加

### 9.1 ホスト（ランナー）が落ちた

ランナーが居なくなった時点で**ゲームとして続行不能**（ガーディアン単独では走れない）。
正直にそう扱う：

1. ガーディアンに「接続が切れました / 復帰を待っています（15秒）」を表示
2. Lobby は**維持**する。EOS Lobby はオーナーが抜けると**自動でオーナー移譲**するので、
   ガーディアンが新オーナーになって部屋が残る
3. 15秒以内に同じ PUID が Lobby に戻れば、**最後のチェックポイントから再開**
   （ガーディアンが保持していたチェックポイント番号を新ホストに渡す）
4. 戻らなければロビーへ

**ホストマイグレーションで走行中の状態を引き継ぐことはしない。** ランナーが居ない以上
引き継ぐ意味が無く、実装コストだけが残るため。

### 9.2 ガーディアンが落ちた

ホストは**シミュレーションを止めない**（止めるとランナーの操作が固まる）。
「ORION の接続を待っています」を出したまま走れる状態を維持し、15秒で
「ソロで続ける / ロビーへ戻る」を出す。ソロ続行は序盤なら成立するが、
**ガーディアン必須の穴が 7 箇所ある**ので、そこで詰むことは明示する。

### 9.3 再接続：**実装する**

モバイルでは切断が日常（アプリのバックグラウンド化、Wi-Fi↔LTE のハンドオーバー）。
そして**このゲームは状態が極端に小さいので、再同期が安い**：

```
RESYNC_FULL {
  tick, ランナー状態(12B), ゲージ(1B), HP(1B), チェックポイント番号(1B),
  生きているホログラム [id, kind, 座標, birth, death] × 最大3,
  既定から逸脱した敵 [id, 位置, hp, 状態] × n,
  ギミック状態 [switch/gate/crumble の id と期限] × m
}
→ 合計 200〜400 B。1 パケットに収まる（EOS の上限 1170 B）
```

**1通で完全復帰できる。** だから再接続は「やる価値がある」ではなく「やらない理由がない」。
アプリ復帰時も、追いつこうとせず無条件に `RESYNC_FULL` を要求する。

### 9.4 途中参加：**実装しない**

2人固定・招待制・1ステージ通しなので、知らない人が途中から入る導線が無い。
`RESYNC_FULL` が既に「途中から世界を受け取る」機能そのものなので、
将来必要になったら**再接続の経路をそのまま使える**。設計上の穴は空けてある。

## 10. チート対策と、P2P 方式の限界

正直に書く。**この構成では、ホスト（ランナー）のチートは防げない。**

### 防げること（ガーディアン＝クライアント側）

ホストは受け取ったコマンドを全部検証する：

| 検証 | 内容 |
|---|---|
| ゲージ | 足りなければ拒否。**クライアントの申告値は一切信用しない** |
| 設置位置 | 地形/既存物との重なり、ステージ範囲内、ランナーからの距離上限 |
| 枚数上限 | 足場2枚・壁1枚。ホストが数える |
| クールダウン | 狙撃 0.6 秒。ホストの時計で測る |
| レート制限 | 1秒あたりの設置/発砲回数に上限。パケット洪水も落とす |
| **`view_tick` の水増し** | 実測 RTT でクランプ。20ms の回線で 250ms 分の巻き戻しは要求できない |
| スコープ中の建築禁止 | ホストが状態を持つ（企画書の中核制約なので特に厳密に） |

### 防げないこと（ホスト＝ランナー側）

ホスト端末が**シミュレーションそのもの**なので、改造されたら：

- 無敵・無限ゲージ・座標テレポート・敵の即死 —— **全部通る**
- 検証する主体が改造されている以上、構造的に検出できない

### なぜそれで良いのか

**このゲームは協力プレイで、PvP もランキングも共有経済も無い。**

- チートの被害は**同意した2人のセッションの中で完結する**
- 得をする相手が居ない（勝つ相手が居ない）
- したがって**チートの動機がほぼ存在しない**

だから**アンチチートに投資しない**という判断を明示的に取る。
「対策していない」ではなく「対策する必要がない構造を選んでいる」。

### EOS Anti-Cheat が使えない理由（正確に）

- **EAC はモバイル（iOS/Android）を対象にしていない。** 本作の主戦場が対象外
- サーバー側 EAC は**専用サーバー前提**。専用サーバーを持たないという最重要条件と矛盾する
- したがって EOS の無料機能のうち EAC だけは**そもそも選択肢に入らない**

### 将来ランキングを付けるなら

P2P では記録を検証できない。取れる道は3つ：

1. **付けない**（推奨）
2. フレンド間だけの**非検証**記録として、そう明記して出す
3. 検証サーバーを立てる → **最重要条件（月額0円）が崩れる**ので、その時に改めて判断する

## 12. Godot × EOS の実装

> 2026-09 実装更新: 協力モードの製品経路は EOSG 2.3.1（revision
> `56238973e2cd7ac9ac99ca14f88934465f0a8997`）を固定し、Connect Device ID、
> Lobby、P2P、EOS Relay fallbackまで実装した。Android/iOSへの組み込みは
> 公開リポジトリの `Mobile Android + iOS` Actionsで検証する。対戦モードは
> 別プロトコルのため未移行で、製品UIから隠している。

正直に言うべきこと：**EOS に Godot の公式サポートは無い。**

| 選択肢 | 状況 |
|---|---|
| `epic-online-services-godot`（3ddelano, GDExtension） | EOS C SDK を包むコミュニティ実装。Windows/Linux/macOS/Android は実績あり。**iOS のビルド構成は要検証** |
| 自前 GDExtension | EOS C SDK は iOS/Android のライブラリを公式に配布している。確実だが工数が要る |
| Godot 標準 `MultiplayerPeer` | EOS 用の実装は存在しない。**`MultiplayerPeerExtension` として自作**すれば、Godot の RPC がそのまま乗る |

**私はこの環境で EOS への実接続を検証できない**（Epic の資格情報が無く、iOS ビルドもできない）。
なので、検証できないものを検証したことにしないために、こう組む：

### トランスポートを抽象化して、ネットコード本体を今すぐ検証可能にする

```
src/net/transport.gd          # インタフェース：send(ch, reliability, bytes) / poll()
  ├─ loopback_transport.gd    # 同一プロセス内・遅延とロスを人工的に注入 ← 今すぐテストできる
  └─ eos_transport.gd         # EOS_P2P_SendPacket / ReceivePacket を呼ぶだけの薄い層
```

ネットコードのロジック（巻き戻し・補間・照合・帯域）は**全部トランスポートの上**に書く。
すると：

- **150ms の遅延と 5% のロスを注入した状態で、救出が成立することをヘッドレスで検証できる**
- EOS 統合は「薄い層を1枚差し替える」作業に縮む
- EOS が iOS で詰まっても、WebRTC 版の薄い層に差し替えれば全部生き残る

**この分割こそが、検証できない依存に対する正しい向き合い方**だと思う。

### 実装順

1. `Clock`（tick 権威）と、移動床・レーザーの決定化 —— **実施済み**
2. `LoopbackTransport` と遅延/ロス注入 —— **実施済み**
3. スナップショットの符号化 / 復号 —— **実施済み**（イベント側はまだ）
4. 巻き戻し＋掃引捕捉＋「助ける方にしか転ばない」判定 —— **実施済み・テスト有り**
5. ガーディアン側の補間・予測・照合 —— **実施済み**
6. `EosTransport`（Connect → Lobby → P2P）—— **実装済み、公開CI/実機検証待ち**
7. 250ms間隔の移譲チェックポイントとLobby owner確定後のhost migration —— **実装済み、実機検証待ち**
8. Android/iOS混在の実機2台で遅延・NAT・relay fallbackを実測

## 13. 検証

ネットワークの設計は「書いた通りに動くか」が目視で分からないので、テストで固定する。

| テスト | 何を固定するか |
|---|---|
| `test_determinism` | 同じ tick から移動床とレーザーが必ず同じ値を出す（＝同期不要である根拠） |
| `test_rescue_under_latency` | **150ms 遅らせた設置要求で、ランナーが実際に助かる**こと |
| `test_rewind_never_harms` | 巻き戻しの結果が不利なら**採用されない**こと。理不尽死が構造的に起きない根拠 |
| `test_rewind_is_bounded` | 250ms を超える巻き戻しを要求されても伸びないこと（水増し対策） |
| `test_bandwidth_budget` | スナップショットが**13 B を超えない**こと、量子化が往復しても壊れないこと、範囲外がラップせずクランプすること |
| `test_loopback_link` | 遅延注入が実際に遅延し、ロスが**信頼チャネルには適用されない**こと（土台が嘘をついていない確認） |

数値ではなく**性質**を固定しているので、実装を触っても性質が壊れたら落ちる。

### 「テストが通った」を信用しないための確認

`test_rescue_under_latency` は、**巻き戻しを無効化すると本当に落ちること**を確認済み。
`MAX_REWIND_TICKS` を 0 にして走らせると 6 チェックが赤くなり、戻すと緑に戻る。
これをやらないと「そもそも遅延していなかったから通った」テストと区別がつかない。

実測（`tools/verify.sh` が毎回印字）：

```
  snapshot: 13 B quiet, 0.4 KB/s at 30Hz
--- 374 checks, 0 failed ---
```

### いま入っているもの / まだ無いもの

**離れていても遊べます。** 2つのトランスポートが入っていて、上に載っている
ネットコードは両方で同じものです——`NetTransport` を挟んだ甲斐がここに出ています。

| | 状態 |
|---|---|
| `Clock`（tick 権威）＋ 移動床・レーザーの決定化 | **入っている** |
| `NetTransport` 抽象と `LoopbackTransport`（遅延/ロス注入） | **入っている** |
| `EnetTransport`（同一 Wi-Fi・直結・中継なし） | **入っている** |
| **`EosTransport`＋EOS Lobby/P2P（インターネット越し）** | **協力モードに入っている。公開CI/実機検証待ち** |

### インターネット越しをどう通したか

直接つなぐには、どちらかが外から届くアドレスを持っている必要があります。
家庭のルーターの内側にいる2人はどちらも持っていません。EOS はこれを
**NAT 越え＋失敗時のリレー**で解きますが、Godot に公式サポートが無く、
**この環境から検証できない**。検証できないものを「実装した」とは書けません。

そこで**検証できる方法**で通しました：`server/signaling/` の Cloudflare Worker を
**中継**に拡張し、Godot 内蔵の `WebSocketPeer`（拡張機能不要・iOS/Android で動く）で繋ぎます。
部屋は既に「相手へ素通し」する作りだったので、**文字列だけでなくバイナリも通す**
数行の変更で中継になりました。

**中継はこのゲームだから成立します。** ランナーの端末がシミュレーションを持つので、
ランナーの入力はネットワークを渡りません。増えた1ホップは**全部ガーディアンに乗り**、
そのガーディアンは数秒先を読んでいて、コマンドは到着時に巻き戻し補償されます（1章・8章）。
**両者がミリ秒の応答を要する設計なら、この取引はできませんでした。**

検証は実物で行いました：ローカルの Worker に Godot から2本つないで、
**両方向のパケットが正しいチャネルで無傷で届く**ことと、
**1170 バイト超が拒否され相手に届かない**ことを確認しています
（`test/ws_probe.tscn` と `server/signaling/test.mjs`）。

### EOS がなぜ今も必要か

中継版には2つの限界があります。

1. **WebSocket は TCP。** パケットが1つ落ちると後ろがつかえます。
   本当の意味での不達許容チャネルが無い。スナップショットは古いものを
   受信側が捨てるので実害は小さいですが、正しい形ではありません
2. **規模が出ると中継が無料でなくなる。** 2人が数人になるうちは Cloudflare の
   無料枠に収まりますが、**「プレイヤーが増えても月額0円」を厳密に保証するのは
   EOS のリレー**（Epic が帯域を負担する）です

つまり**中継版は「いま遊べる」ための答え**で、**EOS は「増えても0円のまま」を守るための答え**。
`NetTransport` を挟んであるので、後者は1ファイルの追加で入ります。

### 実装して分かったこと

**「ランナーに重なる位置には置けない」というルールが、コア体験を禁止していた。**
`BuildAbility._blocked()` はランナーを障害物として数えていて、
落下中のランナーの下に足場を出す——**このゲームの中心にある操作**——が
`blocked` で拒否されていた。最初のエンドツーエンド通信テストがこれで落ちて発覚した。

壁（190px）はランナーを閉じ込めうるので今も拒否する。足場（26px の板）は拒否しない。
薄い板が落下中の体に重なった場合、`move_and_slide` は上へ押し出すので、
結果は「閉じ込め」ではなく「着地」になる。**種類で分けるべきものを一律にしていた。**

もう一つ、**ホログラムの寿命を経過時間から tick に変えた**。2端末が同じフレームで
消す必要があるのに加えて、**バックデートした足場は寿命も短くなるべき**だから
（そうでないと遅延の大きいクライアントが長持ちする足場を買えてしまう）。

**「まだ」のものを「済み」と書かない**ことが、この表の唯一の役目。
