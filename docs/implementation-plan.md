# Kiki 非対称情報ステージの設計（第3回）

## 1. 結論・対象範囲

**「ガーディアンだけが見えるもの」を、個々のオブジェクトではなく *領域*（Veil）として置く。隠す層は領域ごとに宣言する。隠すのは描画だけで、物理には一切触れない。そのうえで、ランナーだけが見える情報も同じ仕組みで作り、会話を一方通行にしない。**

検証用に、既存の実装だけで組める4ビートの短いステージ（1-V "THE QUIET"、全長約3,900px、クリア60〜90秒）を1本作る。新規の本番素材は不要。

- 調査日: 2026-09-16。対象ブランチ: `recovery/unified`。
- 調査基準: **`de11b07`**（`test: fix the fifteen failing checks, none of them in the game`）。fetch後、ローカルとリモート先端の一致を確認した。
- 第2回（地上移動）の設計と実装記録は [`de11b07` の文書](https://github.com/555734/Kiki/blob/de11b07/docs/implementation-plan.md) を参照。その作業は完了し、`tools/verify.sh` は全ステップ green。本書はそれを引き継ぐ第3回。
- **今回の変更は本書のみ。ゲーム実装・素材・テストは一切変更していない。** 以下の「する」「追加する」はすべて次の実装担当への指示。
- 本書中「実測」と書いた数値は、リポジトリ内のGodot 4.4.1（`4.4.1.stable.official.49a5bc7b6`）を headless・`--fixed-fps 60` で走らせて得たもの。「設計値」はまだ動かしていない提案値であり、区別して書く。

## 2. 調査結果 — 今のKikiで何が可能か

実装方針を決めたのはこの節の事実であって、一般論ではない。行番号は調査基準コミットの目安、実装時は関数名で確認すること。

### 2.1 二人の画面はどう分かれているか

| 事実 | 出典 | 設計への意味 |
|---|---|---|
| `Net.OFFLINE` は1台の画面に二人。`HOST`／`CLIENT` は2台に分かれる | `src/main.gd:23-27` | **非対称ステージはオンライン専用。** 共有画面では原理的に隠せない |
| ホスト＝ランナー、クライアント＝ガーディアンで固定 | `src/main.gd:260,270`（`input_hub.solo_role`） | 見えない側が権威を持つ。ずれようがない |
| `solo_role` は既に描画の出し分けに使われている | `src/input/input_hub.gd:309-322`（`owns_runner_controls` / `shows_guardian_cursor`） | 「役割で描画を変える」は新概念ではなく既存の作法 |
| 両端末とも `main._ready()` で `level.build()` を実行する | `src/main.gd:44-54` | **レベル形状は最初から両方の端末にある。** 隠すのは送信の問題ではなく描画の問題 |
| カメラは両端末ともランナー追従。ガーディアンだけ pan と scope を持つ | `src/main.gd:341-352`, `src/guardian/scope.gd` | ガーディアンの情報優位は「範囲」ではなく「先読みと拡大」。設計はこの範囲内で成立させる |

ガーディアンが見通せる前方距離（実測ベースの計算）: viewport 1280 / `CAMERA_ZOOM` 1.5 = 853px、その半分427px + `_pan_limit()` 277px + `CAMERA_LOOKAHEAD` 130px ≒ **ランナーの約834px先**。ギミックはこの距離の内側に置く。

### 2.2 隠しても物理が壊れないことの確認

`visible = false` が当たり判定に影響しないことは、`build/`（git管理外）に一時シーンを置いて実測した。

```
holder.visible      = false
floor drawn?        = false
body landed on it?  = true  y=157.0  (床上面は180、体の半分23 → 正しく着地)
hidden area seen?   = true
```

- 親ノードを `visible = false` にしても、その下の `StaticBody2D` には普通に着地する。
- `visible = false` の `Area2D` も、他の `Area2D` の `get_overlapping_areas()` に出る。

つまり **「見えないが硬い床」「見えないが当たる敵」「見えないが判定するトゲ」は、`visible` を落とすだけで手に入る。** これが本設計の土台であり、推測ではなく確認済みの事実。

なお、`Hazard` には既に `draw_spikes` という「判定はあるが描かない」フラグがあり（`src/levels/level_builder.gd:69` のキル平面が使っている）、この発想自体がコードベースに前例を持つ。

### 2.3 地形は「描画」と「判定」が既に別配線

| 用途 | 読み元 |
|---|---|
| 描画 | `src/render/terrain.gd` の `slabs`（`LevelBuilder.build()` が `Stage.ground()` を代入） |
| 当たり判定 | `LevelBuilder._build_ground_bodies()` が `Stage.ground()` から別途 `StaticBody2D` を構築 |

**同じ配列を2か所が独立に読んでいるだけなので、描画側だけを差し替えれば地形を隠せる。** 判定側には触らない。これが地形を隠す最小の方法。

| 事実 | 出典 | 設計への意味 |

## 3. 中心にある問題 — 「ラジコン化」

依頼文が名指しした失敗形は、次の条件が揃ったときに必ず起きる。

> ガーディアンの情報が **完全** で、**正確に言語化でき**、**伝える時間がある** とき、最適な遊び方は「命令と実行」になる。

だから対策は「ランナーに難しい操作をさせる」だけでは足りない。上の3条件それぞれを崩す必要がある。

| 崩す条件 | 手段 | 本設計での対応 |
|---|---|---|
| 完全性 | ガーディアンにも見えないものを作る | §5.3 封印（ランナーだけが記号を読める） |
| 言語化のしやすさ | 座標を共有させない。代わりに **共有可能な目印** を世界に置く | §6.1 目印の設計 |
| 時間 | 情報の賞味期限を作る | §5.1 動的情報はガーディアン専任・静的情報はランナーが自力で買える |

3つ目が最も効く。**静的情報（床・穴・スイッチ）はランナーが自力で得られる余地を残し、動的情報（敵の位置とタイミング）はガーディアンにしか得られず、しかも数秒で古くなる。** こうするとガーディアンは「先に全部言っておく」ことができない。これが依頼文の「動的情報と静的情報をどう使い分けるか」への答えである。

同じ問題はガーディアン側にもある。**ガーディアンが口だけになる**のを防ぐ原則は1つ。

> **ガーディアンの口と手を、同じ数秒の中で取り合わせる。**

喋っている間は狙えない。狙っている間は喋れない。この配分がガーディアンのゲームプレイであり、ナビゲーター化を構造的に防ぐ。

## 4. どの情報を誰に見せるか — 候補の評価

依頼文の5候補を、Kikiの実装と実測値に照らして評価した。

| 候補 | 実装コスト | 会話の質 | ランナーの技術 | 判定 |
|---|---|---|---|---|
| **敵**（動的） | 低（`visible=false`） | **最高**。情報が古くなるので言い続ける必要がある。「今」「まだ」「戻って」 | 回避は実技 | **採用・主軸** |
| **足場**（静的） | 低（描画配列のフィルタ） | 高。位置の言語化そのものが遊び | ジャンプは実技 | **採用**。ただし単独だとラジコン化しやすく、目印で補強する |
| **スイッチ** | 低 | **反転に使えば最高**。ランナーが喋る側になる | 読みに行く移動が発生 | **採用・反転形で** |
| **落とし穴** | 中（無い床を描く必要がある） | 中。二値で緊急、タイミングは良い | 回避不能になりがち | **限定採用**。宣言された領域の内側でのみ。単独の罠にはしない |
| **ゴール** | 低 | 低。隠し足場の言い換えにすぎない | なし | **不採用** |

### 追加提案（依頼文に無いもの）

1. **領域（Veil）として隠す** — 個別オブジェクトではなく矩形領域に「隠す層」を宣言する。境界はランナーにも見える。
   - *理由*: 「見えないものがある」ことが見える。不意打ちではなく、宣言された盲目になる。失敗が理不尽にならない最大の要因。
   - データが1行で済み、他ステージへの拡張も同じ形で書ける。
2. **反転（ランナーだけが見える情報）** — §5.3。会話を双方向にする唯一の手段。
3. **後追い（失敗時の種明かし）** — §5.4。「理不尽」を「なるほど」に変える。
4. **反響（ランナーの自力探査）** — §5.5。プロトタイプ1には **入れない**。理由は同節。

## 5. 採用する仕組み

### 5.1 Veil（隠し領域）

矩形と、そこで隠す層と、隠す相手の組。

```
{"rect": Rect2(600, 120, 520, 460),
 "hides": ["terrain"],
 "from": "runner",
 "name": "the first step"}
```

- 層: `terrain` / `enemies` / `hazards` / `gimmicks` / `pickups` / `holograms` / `marks`
- 相手: `runner` / `guardian`
- `name` はデバッグ表示とプレイテストのメモ用。ビート名をそのまま入れる。

**隠す = 描かない。それだけ。** 薄く出す、輪郭を出す、事前にヒントを出す — いずれもしない（依頼文の指定どおり）。判定・物理・ネットワークには触れない。

**領域の境界はランナーにも見える。** 地面の色帯、空気の粒、音の変化のいずれか（§13で素材を整理）。ランナーは「ここから先は自分には見えない」と知って入る。

### 5.2 動的情報はガーディアン専任

`enemies` 層を隠した領域では、敵の位置・向き・巡回位相はガーディアンにしか分からない。これは秒単位で古くなるので、ガーディアンは先に言い切ることができない。**これがラジコン化への一番効く歯止め。**

対照的に `terrain` 層は静的で、一度伝えれば終わる。だから地形だけの領域は短くし、**必ず目印（§6.1）を添える**。

### 5.3 封印（反転 — ランナーだけが見える情報）

既存の `ShootableSwitch` + `Gate` + 狙撃をそのまま使う。追加するのは「記号」と、その可視性の向きだけ。

| 要素 | ランナーに見える | ガーディアンに見える |
|---|---|---|
| スイッチが **どこにあるか** | ○ | ○（撃つ対象なので） |
| スイッチに **描かれた記号** | **○** | ✕ |
| 扉が **どの記号を要求しているか** | ✕ | **○** |

どちらも単独では解けない。ガーディアンが「三角が要る」と言い、ランナーが「三角は右の高いやつ」と答え、ガーディアンが撃つ。**会話が双方向になり、ランナーが喋る側に回る唯一のビート。**

間違ったスイッチを撃つと、全スイッチが4秒沈黙する。罰は **時間だけ**（§5.6）。

### 5.4 後追い（失敗時の種明かし）

**領域内でランナーが死んだ／落ちた直後、その端末で1.2秒だけ Veil を解除する。**

これは演出ではなく、設計の中心にある安全装置である。

- 「今のは理不尽だった」が「ああ、*そこ* だったのか」に変わる。
- 次の試行で使える語彙が二人に増える（「さっきの、思ってたより手前だった」）。
- ガーディアンも自分の指示が遅かった／曖昧だったことを目で確認できる。

依頼文の「情報伝達の失敗が理不尽ではなく面白い失敗になるには」への直接の答えがこれ。

### 5.5 反響（ランナーの自力探査）— プロトタイプ1には入れない

設計だけ先に置いておく。

> ランナーが立ち止まって短い操作をすると、半径約180pxの **地形だけ** が0.6秒見える。敵は見えない。音が出るので、隠れている敵が起きる。使用間隔は数秒。

- 静的情報は自力で買える、動的情報は買えない。§3の原則をそのまま道具にしたもの。
- ランナーが「自分で見るか、喋ってもらうか」を選べるので、指示待ちにならない。

**入れない理由**: これは「静的な隠し地形を手探りするのが苦痛」という問題への *対策* である。まずその問題が本当に起きるのかを測るべきで、対策を先に入れると測れなくなる。プロトタイプ1では目印（§6.1）で足りるかを確認し、足りなければこれを次に入れる。

### 5.6 失敗の代価は「時間」であって「進行」ではない

3つの規則。実装担当はステージを作るときこれを守ること。

1. **通信失敗で死なせるのは、死が安い場所だけ。** 学習ビートでは穴の下に安全な棚を置き、登り直させる（6〜8秒）。
2. **一度解いた謎は二度解かせない。** 封印の直後にチェックポイントを置く。答えを知っているパズルの再演ほど退屈なものはない。
3. **正しい情報があれば避けられたはずの失敗だけを死因にする。** 不可避の罠は一つも置かない。

## 6. 会話が成立するための条件

### 6.1 目印 — 共有できる座標系

音声は「右に47px」を運べない。運べるのは **名前** である。だから世界に、**両者に見えて、名前を付けやすく、数えられる** ものを置く。

- 隠す層に入れない装飾（柱、灯、割れ目、色の違う土）を、隠し領域の *内側と縁* に置く。
- 等間隔ではなく不均等に置く。「2本目」と「3本目」が言い分けられる必要がある。
- 最初のビートでは、隠し足場のちょうど両脇に柱を置く（＝答えが名指しできる）。**これは意図的な足場固め**で、ここで「柱で言う」語彙を二人に作らせる。後のビートでは目印を疎にして、同じ語彙を自分たちで延長させる。

依頼文の「伝え方、理解、タイミング、勘違いがゲームプレイになる」は、この語彙づくりそのものを指している。目印はその材料。

### 6.2 時間の圧力

正確な指示ほど長い。短い指示ほど曖昧。**この交換レートが成立するだけの締切**を置く。封印の扉が `hold_time` 秒で閉じる（既存機能）のがそれ。急ぐと「ええと、真ん中！」になり、それが外れる。外れ方が面白い。

### 6.3 ゲーム内マーカー（MARK）の扱い — 要判断

既存の MARK は世界座標に印を出し、両端末に届く（§2.4）。**隠し足場の位置をマーカーで指せてしまうと、会話は置き換えられてしまう。**

| 案 | 内容 | 何が測れるか |
|---|---|---|
| **A（推奨・初期値）** | Veil に `marks` 層を入れ、領域内ではランナー端末にマーカーを描かない | 音声だけで成立するかを純粋に測れる |
| B | 「待て」(kind 2) だけ通す | 停止の合図は非言語でよい、位置は言葉、という切り分けが測れる |
| C | 全部通す | マーカーに頼って会話が減るかを測れる（対照群として1回だけ試す価値はある） |

**プロトタイプ1は A で開始し、プレイテストの最終セットで C を1回だけ試して比較する。** 実装は Veil の層として書けるので、切り替えはデータ1語。

## 7. プロトタイプ設計 — ステージ 1-V "THE QUIET"

### 7.1 案の比較

| 案 | 内容 | 検証価値 | 判定 |
|---|---|---|---|
| A: 隠し足場だけ | 最小。作るのが一番速い | **低い**。最もラジコン化しやすい形だけを測ることになり、一般化できない | 不採用 |
| B: 隠し敵だけ＋反響 | 会話は最も濃い | 中。依頼文の中心にある「静的な隠し地形」を測れない | 不採用 |
| **C: 静的・動的・反転を1本ずつ、短く** | 各1ビート＋最後に組み合わせ | **最高**。3種類を *比較* できるのが最大の収穫。どれが面白くてどれが退屈かが分かる | **採用** |

採用理由: 一種類だけ作ると「このビートは面白かった／つまらなかった」しか分からない。**3種類を同じ長さで並べると、どの非対称が効くかという一般的な答えが出る。** それが今いちばん必要な情報。

### 7.2 全体構成

座標系は既存ステージに合わせる（`FLOOR = 420`、`GROUND_BASE = 900`、`KILL_Y = 1020`）。全長約3,900px、クリア60〜90秒。

```
x:  -900        600   1100        2200   2500  2700      3000
     |  beat0    | b1  |   beat2   |  b3  | b4  |  goal
     助走        隠し   隠し敵      封印   複合
                 足場   （床は見える）
```

| ビート | 長さ | 隠すもの | 相手 | 失敗の代価 |
|---|---|---|---|---|
| 0 助走 | 1,500px | なし | — | — |
| 1 見えない段 | 500px の穴 | `terrain` | runner | 下の棚に落ちる（6〜8秒） |
| 2 動く影 | 1,100px | `enemies` | runner | 被弾1（HP2のうち1）＋ノックバック |
| 3 読めない扉 | 350px | 記号（双方向） | 両方 | 4秒の沈黙 |
| 4 締め | 300px | `terrain` ＋ 扉の残り時間 | runner | 死。ただし直前にチェックポイント |

### 7.3 ビート0 — 助走（x -900 → 600）

平らな床だけ。敵も穴もない。**ここで二人に喋らせる。** 「聞こえてる？」「動くよ」。ステージ名とオブジェクトの表示で「この先、君には見えないものがある」と伝える。

### 7.4 ビート1 — 見えない段（x 600 → 1100）

| 要素 | 値 |
|---|---|
| 床 | `[-1000, 600]` 上面 `FLOOR`(420) |
| 穴 | 600 → 1100（**500px**。スプリントジャンプの実測到達は301pxなので単独では絶対に届かない） |
| 隠し足場 | `[780, 920]` 上面 **330**（床から90px上） |
| 着地先 | `[1100, 2200]` 上面 `FLOOR` |
| 救済棚 | `[600, 1100]` 上面 **560**（床から140px下。スプリントジャンプ193pxで登り返せる） |
| Veil | `Rect2(600, 200, 500, 500)`、`hides: ["terrain", "marks"]`、`from: "runner"` |
| 目印 | 柱（装飾、隠さない）を x=780 と x=920 に。**隠し足場の両端にちょうど重なる** |

到達性の確認（実測値による計算）:
- 床(420) → 足場(330): 水平180px・垂直90px。スプリントジャンプ 301×193 の内側。**余裕あり。**
- 足場(920, 330) → 着地先(1100, 420): 水平180px の落下。**歩いても届く。**

失敗すると棚(560)に落ちる。x=600 の壁を140px登れば戻れる。**死なない。**

**ガーディアンの選択肢**: 会話で渡らせる（無料）か、自分の足場を30払って置く（確実だが5秒で消える）。ここで「喋る方が安い」ことを体で覚えさせる。

> **既知の弱点**: このビートはガーディアンの手が空く。プレイテストで「ガーディアンが暇だったか」を必ず聞くこと。暇だった場合の対策は §7.9 のバリアントB。

### 7.5 ビート2 — 動く影（x 1100 → 2200）

| 要素 | 値 |
|---|---|
| 床 | 平坦・**完全に見える**。ここでランナーは盲目ではない |
| 敵 | `walker` ×2。`pos (1500, FLOOR-21) patrol 180` と `pos (1900, FLOOR-21) patrol 150` |
| Veil | `Rect2(1150, 100, 1050, 600)`、`hides: ["enemies", "marks"]`、`from: "runner"` |
| チェックポイント | x=1150 |

**床が見えるのでアクションゲームのままである。** 隠れているのは動くものだけ。ウォーカーは 44×42px、静止ジャンプ162pxで容易に跳び越せる — **いつ跳ぶかを知っていれば。**

情報が数秒で古くなるので、ガーディアンは「1体目は今こっち向き、2体目は奥で折り返した」と言い続けることになる。これが本設計でいちばん会話が濃くなる場所だと予想している。**プレイテストの第一の観察対象。**

### 7.6 ビート3 — 読めない扉（x 2200 → 2700）

| 要素 | 値 |
|---|---|
| 扉 | `Gate` at x=2500、`span (40, 190)`、床に接地、`hold_time` 6.0秒 |
| スイッチ | `ShootableSwitch` ×3: `(2380, FLOOR-260)` / `(2560, FLOOR-150)` / `(2640, FLOOR-300)` |
| 記号 | 三角・四角・丸を固定配置（プロトタイプ1では乱数化しない、§10.5） |
| ランナーに見える | スイッチ上の記号 |
| ガーディアンに見える | 扉が要求する記号 |
| 誤射 | 全スイッチ4秒沈黙。扉は開かない |

スイッチは高い位置にあり、ランナーは **記号を読むために動いて見上げる必要がある**（＝指示待ちの姿勢では解けない）。ガーディアンは撃つ対象を選ぶ必要がある（＝口だけでは解けない）。

会話は必ず双方向になる。片方だけが喋って解ける組み合わせが存在しない。

### 7.7 ビート4 — 締め（x 2500 → 3000）

扉は6秒で閉じる。その向こうに、ビート1と同じ形の穴がもう一つ。ただし **目印は無く、下は本物の穴（死）**。

- ガーディアンは扉の残り時間を見ながら、位置も言わなければならない。**口と手と時計が同時に要る。**
- ランナーは文が終わる前に踏み切らざるを得ない。**命令の実行ではなく解釈になる。**
- チェックポイントは扉の直後（x=2520）。死んでもパズルは再演しない（§5.6-2）。

ゴール x=2950。

## 8. 1ステージ内の段階的発展（本番ステージ向け）

プロトタイプで方針が確認できたら、本番ステージはこの順で組む。**各段は前段の語彙を使い、新しい要素は必ず1つだけ足す。**

| 段 | 教えること | 新しい要素 | 死 |
|---|---|---|---|
| 1 | ガーディアンには見えている | 隠し地形（短い・目印あり・安全） | なし |
| 2 | 情報には賞味期限がある | 隠し敵（床は見える） | 被弾のみ |
| 3 | 自分にも道具がある | 反響（§5.5、入れるなら） | なし |
| 4 | 自分も情報を持っている | 封印（記号の反転） | なし |
| 5 | 注意は有限 | 隠し地形＋隠し敵の同時、ガーディアンは撃ちながら喋る | あり |
| 6 | 締切がある | 上に時間制限（扉／既存の追跡敵） | あり |

**5を4より前に置かないこと。** 反転（4）を経験する前に注意の奪い合い（5）を出すと、ランナーは「情報を持つ側」を一度も体験しないまま最も難しい場面に入る。

## 9. 依頼文の各問いへの回答（要約）

| 問い | 回答 |
|---|---|
| どの情報をどちらに見せるか | 動的（敵）はガーディアン専任。静的（地形）は領域で隠すが目印を添える。記号は反転させてランナー専任にする |
| どのギミックが通話を面白くするか | 賞味期限のあるもの＝隠し敵が最も濃い。次に反転。静的な隠し地形は単独では弱く、目印か時間制限と組む必要がある |
| どれを組み合わせるか | 隠し地形×時間制限（最良）。隠し敵×見える床（安全に濃い）。反転×狙撃（双方向の唯一の形）。隠し地形×隠し敵は最終段に取っておく |
| どの順序か | §8 の6段。反転は注意の奪い合いより前 |
| ランナーが指示待ちにならないために | ①実技が残る難度 ②複数の攻略線 ③記号という自分だけの情報 ④文が終わる前に踏み切らせる締切 ⑤（v2）反響 ⑥停止するかどうかはランナーが決める |
| ガーディアンがナビにならないために | ①口と手を同じ秒に取り合わせる ②言えることは大体ゲージでも解けるが逆は成り立たない ③ガーディアンにも見えないものがある ④視界が有限で「どこを見るか」の選択がある |
| 失敗を面白くするには | §5.4 後追い（1.2秒の種明かし）＋ §5.6 三原則（安い死・パズルを再演させない・不可避の罠を置かない） |
| 動的と静的の使い分け | **静的はランナーが自力で買えるようにし、動的はガーディアンの専任にする。** そうすればガーディアンは先に言い切れず、ランナーは手探りを強制されない |
| 既存システムの活用 | 実技の難度はジャンプ実測値（301×193）で設計。壁キックと三段ジャンプは隠し地形の別解として残す。狙撃は反転の実行手段。足場は「喋る代わりに金で解く」対抗手段。既存の Gate / ShootableSwitch / walker / moving_platform / turret をそのまま使う |

## 10. 実装設計（技術）

### 10.1 全体方針

**追加するのは「描画を役割で間引く1つの仕組み」だけ。** 物理・ネットワーク・既存エンティティには触らない。

新規ファイル:

| ファイル | 役割 |
|---|---|
| `src/levels/veil.gd` (`class_name Veil`) | 層と相手の定数、役割の解決、矩形判定。RefCounted の静的ユーティリティ |
| `src/render/veil_field.gd` | Veil を実際に適用するノード。`LevelBuilder` が1つ作る |
| `src/levels/level_quiet_data.gd` | ステージ 1-V のデータ |
| `test/veil_probe.gd` / `.tscn` | §11 の自動検査 |

変更ファイル:

| ファイル | 変更 |
|---|---|
| `src/levels/stage.gd` | `Which.QUIET` と `veils()` を追加。他の accessor と同じ形 |
| `src/levels/level_builder.gd` | VeilField を作り、地形の描画配列を通し、動的ノードを登録する |
| `src/entities/gimmicks/shootable_switch.gd` | `sigil: int` を追加。ランナー端末でのみ記号を描く |
| `src/entities/gimmicks/gate.gd` | `wants: int` を追加。ガーディアン端末でのみ要求記号を描く |
| `src/ui/net_panel.gd` | ステージボタンを1つ追加。オフラインでは選べないことを表示 |
| `tools/verify.sh` | veil probe を追加 |

### 10.2 Veil

```gdscript
class_name Veil
extends RefCounted

## 隠す層。文字列で持つのは、レベルデータの他の行（"type": "walker" など）と
## 書き方を揃えるため。
const LAYERS := ["terrain", "enemies", "hazards", "gimmicks",
	"pickups", "holograms", "marks"]

## この端末は誰の目か。"" はオフライン（=両方見える）。
static func eye(hub: InputHub) -> String:
	if _forced != "":
		return _forced          ## 開発用。§10.6
	return hub.solo_role if hub != null else ""

static var _forced: String = ""
static func force_eye(role: String) -> void:
	_forced = role
```

### 10.3 VeilField

```gdscript
extends Node2D
## レベルデータの Veil を、この端末の役割に合わせて適用する。
##
## 隠すのは描画だけ。当たり判定・物理・送信には触れない。visible=false が
## 当たり判定に影響しないことは実測で確認済み（設計書 §2.2）。

var veils: Array[Dictionary] = []
var hub: InputHub = null

func hidden(layer: String, at: Vector2) -> bool
func filter_slabs(slabs: Array[Rect2]) -> Array[Rect2]   ## 地形の描画用
func watch(node: Node2D, layer: String, moving: bool) -> void
func reveal_for(seconds: float) -> void                  ## 後追い（§5.4）
func _process(delta: float) -> void                      ## 動くものだけ再判定
```

- `watch()` は `LevelBuilder.rebuild_dynamic()` から呼ぶ。型はそこで分かっているので、エンティティ側のコードは **1行も変えない。**
- `moving == false` のノードは登録時に一度だけ評価する。毎フレーム見るのは敵と移動床だけ（数個）。
- `reveal_for()` は `Events.runner_died` と落下検出で呼ぶ。

`LevelBuilder.build()` 側:

```gdscript
_terrain.slabs = _veils.filter_slabs(Stage.ground())   ## 描画だけ
_build_ground_bodies()                                  ## 判定は Stage.ground() のまま
```

**この2行が隣り合っていることが重要。** 片方だけ変えたくなったときに、もう片方が目に入る。

### 10.4 ネットワーク

**隠蔽そのものに通信の変更は要らない。** 両端末が同じ静的データからレベルを作るので、隠すかどうかは各端末のローカルな描画判断である（§2.1）。

ただし、以下は **別途対応が必要**。

| 項目 | 現状 | 必要な対応 | 優先度 |
|---|---|---|---|
| ステージ選択が同期しない | 両者が手で同じものを選ぶ | `HELLO` にステージ番号を1byte足し、不一致ならハンドシェイクを拒否して両画面に理由を出す。`Protocol.VERSION` を 9→10 | **高**。非対称ステージで食い違うと、症状が「相手がおかしい」にしか見えず、デバッグ不能になる |
| オフラインで非対称ステージが成立しない | 両方見えて素通し | ステージ選択で「2台専用」と表示し、オフラインでは選択不可にする | **高** |
| 記号配置を乱数化したい（v2） | 固定 | `WELCOME` に seed を4byte足し、両端末が同じ配置を作る | 中。プロトタイプ1は固定でよい |
| カウントダウンが同期しない | ローカルのみ | `Protocol.World` に kind を1つ足す | 低。使うなら |

**変えてはいけないもの**: Snapshot の幅（14byte）、State の3bit、`ENEMY_RADIUS`、クライアントが物理を止める構造、`HostAuthority` の巻き戻し救済。いずれも非対称化と無関係であり、触る理由がない。

### 10.5 ステージデータ

既存の作法（静的メソッドが `Array[Dictionary]` を返す）をそのまま踏襲する。`Stage` に `veils()` を1つ足す以外、構造を変えない。

```gdscript
static func veils() -> Array[Dictionary]:
	return [
		{"rect": Rect2(600, 200, 500, 500),
		 "hides": ["terrain", "marks"], "from": "runner",
		 "name": "the first step"},
		{"rect": Rect2(1150, 100, 1050, 600),
		 "hides": ["enemies", "marks"], "from": "runner",
		 "name": "the moving dark"},
		{"rect": Rect2(2700, 200, 300, 500),
		 "hides": ["terrain", "marks"], "from": "runner",
		 "name": "the last step"},
	]
```

記号は既存の gimmick 行を拡張するだけ:

```gdscript
{"type": "switch", "id": "quiet_gate", "pos": Vector2(2380, 160), "sigil": 1},
{"type": "gate",   "id": "quiet_gate", "pos": Vector2(2500, 325), "wants": 3},
```

**他の非対称ステージへの拡張は、このデータを書くだけで済む。** 仕組み側に手を入れる必要はない。

### 10.6 開発とデバッグ

- `Veil.force_eye("runner")` でオフライン1台でもランナー視点を再現できる。probe とスクリーンショット取得はこれを使う。
- デバッグ表示: `F3` 等で Veil の矩形と `name` を枠表示する（ガーディアン端末のみ）。実装担当は自分の作ったステージが何を隠しているか目で確認できる必要がある。

**自動テストで測れないこと**を明記しておく: 会話が必要だったか、面白かったか、退屈しなかったか。これらは §12 でしか測れない。**テストが全部通ったことは、このコンセプトが成立した証拠にならない。**

## 12. プレイテスト設計（これが本番）

### 12.1 手順

- 2人1組、**別々の部屋**（画面が見えない）、音声通話あり。3組以上。
- 1組あたり: 1-V を3回 → 役割交代 → さらに3回。
- 録音する（または観察者が発話回数を数える）。**会話の量と質が主データである。**
- 観察者は各ビートの所要時間・死亡回数・沈黙の長さを記録する。

### 12.2 記録する数値

| 指標 | 取り方 | 合格の目安 |
|---|---|---|
| ビートあたりの発話回数 | 録音から | **2回未満のビートは非対称になっていない**（片方が黙っていても解けた） |
| ガーディアンの無言連続時間（ビート1） | 秒 | 8秒を超えたら「暇」。バリアントBを検討 |
| ビート1の初回突破試行回数 | 回 | 中央値5回超なら手探りが苦痛 → 反響（§5.5）を投入 |
| ビート3の解決時間 | 秒 | 20〜60秒が狙い。20秒未満は簡単すぎ、90秒超は記号が読みにくい |
| 2回目以降の所要時間短縮 | % | 短縮しているなら「語彙が育っている」＝設計が効いている |
| 役割交代後の主観評価差 | 下記5問 | 片方の役割だけ評価が低いなら、その役割が受け身になっている |

### 12.3 聞く質問（依頼文の5点をそのまま instrument にする）

各ラウンド後、両者に5段階で:

1. **本当に会話が必要だったか**（1=黙っていても解けた / 5=喋らないと無理）
2. **会話そのものが面白かったか**（1=作業だった / 5=会話が楽しかった）
3. **自分は暇だったか**（1=ずっと暇 / 5=ずっと忙しい）— *ビートごとに聞く*
4. **指示を聞くだけだったか**（ランナーのみ。1=言われたとおり動いただけ / 5=自分で判断していた）
5. **失敗したあと、もう一度やりたくなったか**（1=理不尽で萎えた / 5=すぐ試したかった）

自由記述で「相手にいちばん伝えにくかったこと」を1つ挙げてもらう。**ここに次の設計のネタが出る。**

### 12.4 判断基準（次に何をするか）

| 観察 | 結論 | 次の一手 |
|---|---|---|
| ビート2（隠し敵）の評価が最も高い | 動的情報が主軸で正しい | 本番ステージを動的中心で組む |
| ビート1の評価が低く試行回数が多い | 静的な隠し地形は単独では成立しない | 反響（§5.5）を入れて再測。改善しなければ、静的隠しは常に時間制限か目印と組ませる |
| ビート3の評価が最も高い | 反転が効く | 反転をもっと増やす。記号以外の反転（音・数・順序）を設計する |
| ランナーの質問4が低い（全ビート） | ラジコン化している | 締切を短くし、攻略線を増やし、反響を入れる |
| ガーディアンの質問3が低い | ナビ化している | §3の原則に戻り、口と手が衝突する場面を増やす（バリアントC） |
| 質問5が低い | 失敗が理不尽 | 後追いの秒数を延ばす。死を棚落ちに置き換える。チェックポイントを増やす |
| 全体的に評価が低い | **コンセプト自体を見直す** | 隠すのをやめ、「解像度の違い」（両者見えるが精度が違う）など別の非対称を検討する |

最後の行を書いておくことが大事である。**このコンセプトが面白くない可能性を、設計の中に持っておく。**

## 13. 素材の整理

**プロトタイプ1に必要な新規の本番素材は、ゼロ。**

| 分類 | 内容 | 判断 |
|---|---|---|
| **既存でそのまま** | 地形、柱・木・看板（目印に使う装飾）、walker、turret、moving_platform、Gate、ShootableSwitch、スイッチON/OFFのSVG、狙撃の演出、チェックポイント、ゴール | 追加不要 |
| **仮素材で十分（手続き描画）** | 記号3〜4種（三角・四角・丸・十字）は `draw_` で描く。Veil の境界表示も色帯か粒子で `_draw()` に書く。後追いのフェードも同様 | **コンセプトが成立してから**本制作。コードベースは元々ほぼ全部を手続き描画しており（`terrain.gd`, `decor.gd`, `shootable_switch.gd`）、これは逸脱ではなく作法どおり |
| **仮で流用** | Veil に入る／出るときの音は既存の `checkpoint` か `gate` を流用 | 専用音は後 |
| **成立後に本制作すべきもの** | ① Veil 境界の見た目（「ここから見えない」を一目で伝える最重要の絵） ② 記号のアイコン（読み間違いが *面白い* 程度に似ていて、*理不尽* にならない程度に違う — これは実際に遊んでから決めるべき） ③ 後追いの演出 ④ 専用BGM／環境音 | **いずれもプレイテスト後。** 特に②は、どのくらい紛らわしいかが遊んでみないと決まらない |

**この順序を守る理由**: 記号のアイコンを先に作ると、その見た目に合わせて難易度が決まってしまう。先に手続き描画の粗い記号で遊び、「もう少し似ている方が面白い」「これは似すぎ」を測ってから描く。

## 14. 実装順序

## 15. 採用しなかった案と理由

| 案 | 理由 |
|---|---|
| ランナー画面に薄く／輪郭で表示する | 依頼文が明示的に否定。加えて、薄く見えると会話が「確認」に退化する。見えないか見えるかの二値の方が会話が要る |
| ゴールを隠す | 隠し足場の言い換えで、新しい会話を生まない |
| 単独の隠し落とし穴（領域の宣言なし） | 正しい情報があっても避けられない瞬間が生まれうる。§5.6-3 に反する。加えて「自分の目を信じるな」を教えてしまい、他のステージまで壊す |
| ガーディアンにステージ全体を見せる（俯瞰マップ） | カメラ構造の大改修になり、かつ情報が完全になってラジコン化を加速する。現在の pan 制限（±277px）は **制約ではなく設計資産** である |
| 画面共有を前提にした暗号・手順書（Keep Talking 型の完全な分離） | Kikiは横スクロールアクションであり、手順書を読む時間はアクションを止める。記号1個の反転（§5.3）が、この方向でアクションと両立する上限だと判断した |
| 隠蔽をサーバー権威で行う（ランナー端末にデータを送らない） | 協力ゲームに不正の脅威モデルは無い。送らない方式は `LevelBuilder` の二重化を招き、同期のバグ表面を増やすだけで、得るものがない |

## 16. 未解決・実装担当が判断すること

1. **MARK の扱い（§6.3）。** A で始めることを推奨するが、最終判断はプレイテストの比較で。
2. **Veil 境界の見せ方。** 「ここから見えない」をどう伝えるか。案: 地面の色帯／空気の粒／画面端のビネット／音。**最初の実装は最も安い色帯でよい**が、これが伝わらないと全部が理不尽になるので、プレイテストで最初に確認すること。
3. **後追いの秒数。** 1.2秒は設計値であり実測ではない。短いと何も分からず、長いと「見えてしまう」。0.8〜2.0秒で調整。
4. **記号の似せ具合。** §13の②。遊んでから決める。
5. **ビート1でガーディアンが暇な問題。** バリアントB（移動する隠し足場）が第一候補だが、初回ビートとして難しすぎる可能性がある。プレイテストで両方試すこと。
6. **オフライン時の扱い。** 選択不可にするのが安全だが、開発中は `force_eye` で1台確認できる必要がある。両立させること。

## 17. この設計が守っていること

- **物理を変えない。** 隠すのは描画だけ。二人は必ず同じ世界を遊ぶ。
- **通信を増やさない。** Snapshot も World も既存のまま（ステージ同期の1byteを除く）。
- **既存エンティティのコードをほぼ変えない。** 敵・床・トゲは自分が隠されていることを知らない。
- **データで増やせる。** 次の非対称ステージは `veils()` と既存ギミックを書くだけ。
- **失敗が安い。** 通信の失敗は時間を失うだけで、進行を失わない。
- **面白くなかった場合の逃げ道がある。** §12.4 の最終行。

### 18.1 最重要の不変条件

### 18.3 設計から変えたところ（実装して分かったこと）

1. **MIDをFLOORより高くした。** §7.4の救済棚は、そのままだと「落ちて棚を歩いて渡る」という抜け道になる。棚(560)から向こう岸への上りが140pxで、静止ジャンプ162pxの内側だったため。向こう岸をMID=340（手前のFLOOR=420より80px高い）にして、棚からの上りを220pxにした。スプリントジャンプ193pxの外側で、壁キック（反対向きに飛ぶ）でもリップ掴み（手が届かない）でも抜けられない。**設計の見落としで、幾何を置いて初めて見つかった。**
2. **ビート4の穴を300→420pxに広げた。** 設計の300pxは、実測のスプリントジャンプ到達301pxの内側で、ガーディアン抜きで飛べてしまう。**設計自身の数値が設計自身の意図を壊していた。**
3. **踏み切り可能幅を実測した。** ビート1は x=523〜591、ビート4は x=2620〜2700。どちらも約70px＝0.17秒の窓。ピクセル単位ではないが、どこで跳ぶかを知らなければ当たらない。狙った難度に入っている。
4. **最後のジャンプはそのままゴールに着地する**（着地x=3312、ゴール3350）。結果的に「渡り切った瞬間にクリア」になり、終わり方としては悪くないのでそのままにした。probe側は全行程を通して `stage_cleared` を監視するように直した。
5. **誤射のフィードバックは `Events.shot_blocked` を再利用した。** 「当たったが何も起きなかった」は既にこの signal の意味そのもので、ガーディアン端末への中継（`World.SHOT_BLOCKED`）も火花も音も既にある。**新しい signal も新しい World kind も足していない。**
6. **反響（§5.5）は実装していない。** 設計どおり。まず目印で足りるかを測る。
7. **バリアントB/C/D（§7.9）は実装していない。** いずれも `level_quiet_data.gd` のデータ編集だけで足りる（Bは `ground()` の隠し足場を `gimmicks()` の `moving_platform` に、Cは `enemies()` に turret を1行、Dは `veils()` の `"marks"` を消す）。プレイテストで比較するときに切り替える。

### 18.4 実装中に踏んだ罠（次の担当者向け）

- **解放済みインスタンスを型付き変数に代入すること自体がエラーになる。** `var n: Node2D = entry["node"]` は `is_instance_valid()` に到達する前に落ちる。敵は撃たれるたびに監視リストの下で解放されるので、無型で受けてから確認する（`VeilField._alive`）。
- **GDScriptのラムダはbool等を値でキャプチャする。** `stage_cleared` を待つフラグが永久に false のままになる。既存 probe が1要素配列を使っているのはこのため。
- **新しい `class_name` は editor import を通すまで `check_scripts` から見えない。** `level_horror_data.gd` が class_name を避けている理由と同じ根。1-Vのデータも同じく preload で参照している。

### 18.5 2台での確認手順（プレイテスト前に一度）

1. 両端末で **1-V を選ぶ**。片方だけ選び忘れた場合は接続時に「ステージが違います（相手 1-1 / こちら 1-V）」と出て、ハンドシェイクは成立しない（§10.4で高優先とした穴は塞いだ）。
2. オフライン（1台で2人）ボタンは 1-V 選択中は押せず、「このステージは2台専用です」と表示される。
3. 部屋を作った側がランナー（隠される側）、入った側がガーディアン。
4. 開発中に1台でランナーの見え方を確認したいときは `Veil.force_eye("runner")`。

### 18.6 まだ確認できていないこと

**このコンセプトが面白いかどうかは、まだ1ミリも分かっていない。** 自動テストが保証したのは「隠蔽が物理を変えない」「隠したものが見えない」「ステージが理論上クリアできる」の3つだけで、§12の5つの問い — 本当に会話が必要だったか、会話が面白かったか、片方が暇にならなかったか、指示待ちにならなかったか、もう一度やりたくなったか — はどれも人間2人でしか測れない。次は §12 のプレイテストであり、その結果次第では §12.4 の最終行（コンセプト自体の見直し）もそのまま有効である。
